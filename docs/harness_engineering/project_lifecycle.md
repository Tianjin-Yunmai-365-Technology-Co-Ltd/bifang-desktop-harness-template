# 范围、生命周期、维护与演进

## 5. MVP 范围闸门

任何拟加入当前版本的需求，都依次回答以下问题：

1. 没有它，核心用户能否完成唯一目标？
2. 它是在提高核心流程的正确性和可靠性，还是增加新的使用方式？
3. 需求来自真实使用，还是来自对未来的想象？
4. 能否通过已有系统或更简单的方式解决？
5. 它引入多少新的状态、依赖、权限和失败模式？
6. 它是否改变当前版本的成功标准？
7. 如果延后到下一个版本，用户会损失什么？

判断原则：

- 缺少它会导致核心目标无法完成：进入 MVP。
- 缺少它会导致数据损坏、结果失真或无法合理使用：作为可靠性工作进入 MVP。
- 它只是提供更多选择、更高级体验或潜在扩展：进入未来版本候选。
- 无真实证据且增加明显复杂度：拒绝。

## 6. 面向 Codex 的项目 Harness

### 6.1 人负责方向，代理负责执行

人的主要责任是：

- 选择值得解决的问题。
- 给出真实约束和取舍。
- 确认产品边界。
- 对用户体验和风险做最终判断。
- 验收结果是否解决真实问题。

编码代理的主要责任是：

- 阅读仓库事实。
- 提出可验证的实现方案。
- 修改源码和文档。
- 执行测试、构建和检查。
- 报告证据、风险和未完成事项。
- 将新知识沉淀回仓库。

### 6.2 给地图，不给百科全书

代理入口文档应短小，主要回答：

- 项目目标是什么？
- 关键文件在哪里？
- 哪些规则必须遵守？
- 应执行哪些验证？
- 深入资料在哪里？

详细内容应分散在规格、架构、计划、测试和发布文档中，并通过入口文档建立链接。

### 6.3 约束必须可检查

重要规则不能只写成希望。能机械检查的约束，应逐步转化为：

- 类型系统。
- 测试。
- 格式化或代码规范检查规则。
- 构建脚本。
- CI 检查。
- 发布清单。

只有当规则重复出现并且人工检查容易遗漏时，才值得自动化。

### 6.4 每次任务留下可接手状态

一次工作结束时，应在最终回复、CI 或被触发的持久记忆中明确记录：

- 修改了什么。
- 为什么这样修改。
- 执行了哪些验证。
- 哪些验证没有执行。
- 是否存在工作区未提交修改。
- 下一步是什么。
- 是否改变了规格、版本或技术债。

日常开发通常只在最终回复和测试/CI 中记录结果；只有用户明确要求持久计划、跨会话需要恢复、出现重要阻断、发布、完整验收或长期审计时，才把对应事实写入 Work Plan、Product Status 或 Verification。

## 7. 标准三段式版本管理

个人小工具同样需要让用户能判断当前版本是否兼容、是否值得升级，因此版本管理不能是发布前临时补的动作，而应该从第一次可运行 MVP 起就存在。

版本管理的可执行规则（Harness 上海时区时间版本、下游语义化版本规范 2.0.0、已发布版本不可覆盖和发布门禁等）由 `docs/RELEASE.md` 统一维护；Harness 模板当前版本、时间版本起始值、旧版本标识与发布状态只由根目录 `Version.md` 记录。本节只保留为什么严肃对待版本号这一背景动机，不再重复具体规则，避免出现多份可能漂移的版本规范。

## 8. 发布物命名与版本认知

发布物命名同样只保留一份权威来源：Rust 下游产品的归档命名模式（`<product>-v<version>-<platform>-<arch>.<ext>`，附带 `.sha256` 与清单）已在 `docs/RUST_CLI_TEMPLATE.md` 给出，模板自身源码归档命名见 `docs/RELEASE.md`。

本节保留的背景动机是：文件名、Git 标签和发布标题里的版本必须让人一眼确认彼此对应。Harness 使用 12 位时间版本，下游默认使用 `MAJOR.MINOR.PATCH`，`v` 只是面向人识别的前缀；具体示例和字段级规则不再在此重复。

## 9. CHANGELOG 与升级说明

CHANGELOG 是用户和维护者感知“这个版本到底变了什么”的正文来源，缺失或敷衍会让升级和排障都失去依据。

可执行规则——按日文件命名、分类、何时必须更新、不兼容变化如何标注——已收敛到 `docs/changelog/README.md`，`AGENTS.md` 的事实来源表也指向该文件作为合格用户和维护者可见变化的唯一正文来源。普通缺陷修复即使用户可感知也不进入 Changelog，纯重构、格式整理、测试补强和内部清理同样不记录；若任务另含新增、行为/契约变化、移除或安全事项，只记录该独立部分。

## 10. 维护状态与用户建联

维护状态和反馈入口属于用户认知的一部分（见[基础分卷 3.7](foundations.md#37-用户认知是交付的一部分)）：用户应当知道软件是否还有人维护、遇到问题去哪里反馈。

这条原则目前没有独立的自动化 validator 门禁，但已在 `docs/ENGINEERING_RULES.md` 的文件职责表中正式列为 `README.md` 的唯一职责之一，因此保持简短：README 至少标注一种维护状态（Active / Maintenance / Paused / Archived），并至少提供一种持久反馈入口；停止维护时保留历史源码并说明最后可用版本和已知重要问题。极简工具不应为了建联而增加账户、遥测或强制联网。

## 11. 最小项目资产

一个准备长期维护的小工具，建议至少包含：

```text
README.md                  用户用途、运行前提、使用方式、维护状态、反馈入口
docs/adr/                  按日保存产品边界变化、长期决定与硬规则例外
docs/changelog/            按日保存用户和维护者可见变化
docs/                      规格、重要决定和必要参考
src/                       源码
tests/                     核心闭环和风险测试
版本清单                  唯一版本事实来源或受控同步来源
构建配置                  可生成真实发布物
```

按需增加而非默认增加：

- `AGENTS.md`：本 Harness 产出的每个项目都强制、永久包含该文件——其 Skills 地图与约束地图是 `AGENTS.md` 自身声明的永久结构，初始化与后续裁剪都不会移除它，这不是等待某个触发条件才增加的可选项；只有完全不经由本 Harness 生成、且从未有编码代理参与的项目，才需要自行判断是否引入等价文档。
- `ARCHITECTURE.md`：当模块关系已无法通过源码目录直接理解时增加。
- 执行计划：复杂、跨多步或需要跨会话推进时增加。
- CI：当人工验证开始重复、发布给其他用户或多人协作时增加。
- 自动发布：当手工发布频繁出错且发布频率足以抵消维护成本时增加。

## 12. 新项目启动模板

新产品启动时把“一句话目标、真实问题、输入输出、MVP 范围、约束、数据流、错误与可靠性、成功标准、验证、版本发布、用户建联、已知风险”逐项写清楚，这件事本身仍然成立；对已有批准产品的日常改动则不重复立项。`$desktop-define-product` 只在新产品、需求模糊或产品目标/边界/成功标准变化时采集并落盘规格。

## 13. 阶段检查清单

阶段检查按事件触发组合：新产品/边界变化使用 `$desktop-define-product`；日常开发直接使用 `$desktop-implement-change`；用户明确要求持久计划或跨会话协调时先用 `$desktop-plan-change`；发布候选或用户明确要求完整验收时使用 `$desktop-verify-delivery`，发布再进入 `$desktop-prepare-release`。日常维护不为形式完整重复所有阶段。

## 14. Harness 的积累与演进

不是每次项目经验都应该变成永久规则。只有满足以下条件之一时，才考虑升级为通用 Harness：

- 同类问题在多个项目中重复出现。
- 问题造成过真实失败、返工或用户损失。
- 人工检查容易遗漏，且规则可以清楚验证。
- 新规则能降低未来项目的认知或交付成本。

沉淀顺序应由轻到重：

```text
经验记录 → 清单条目 → 项目规则 → 自动检查 → 通用工具
```

避免以下反模式：

- 因一次偶然问题增加永久复杂流程。
- 把个人审美包装成必须遵守的工程规则。
- 为了体现“工程化”创建无人维护的文档和脚本。
- 让 Harness 文档比实际项目更难理解。
- 规则已经失效但仍继续注入代理上下文。
- 自动化成本超过它预防的问题成本。

Harness 应定期清理。过时规则和错误上下文会比缺少规则更危险。
