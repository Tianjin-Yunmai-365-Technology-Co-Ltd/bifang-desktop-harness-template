# CLI 机器接口契约

本文档是选择 CLI 的下游项目机器接口最低契约。CLI 本身可不选择；一旦初始化或产品范围包含 CLI，就不得削弱以下要求。未选择 CLI 的项目把本契约明确记为不适用。

## 调用模式

- 产品规格仍为 `Draft` 的中性 Rust 脚手架只允许 `scaffold status`；其成功 JSON 数据包含 `productDefinitionRequired=true`。该命令是生命周期提示，不是业务命令，必须在产品定义获批后的实施中被删除或替换。
- CLI 的目录、Cargo 包、Rust crate 和真实二进制文件名称由当前 ASCII `snake_case` 项目标识确定性派生为 `<项目标识>_cli`；初始化不得另行询问或配置二进制文件名称。
- 所有核心操作必须支持完全非交互调用。
- 所有核心操作必须支持 `--json`。
- JSON 模式的标准输出只能包含一个完整 JSON 文档，不得混入日志、进度条、颜色或解释文本。
- 日志、警告、进度和诊断信息写入标准错误。
- JSON 模式不得因缺少交互输入而等待；缺少参数时立即返回参数错误。
- JSON 文档使用 UTF-8 编码，不写 BOM，并以一个换行结束。
- 每个 CLI 至少提供 `--help` 和 `--version` 或产品规格中记录的等价只读入口，用于帮助、版本核对和启动冒烟测试。
- 删除、覆盖或其他破坏性操作必须要求显式确认参数；完全非交互调用不得自行确认。

## 标准输入

- 不需要标准输入的命令不得阻塞等待标准输入；无论标准输入是否被管道连接、是否为终端，都必须立即按参数执行或返回参数错误。
- 通过标准输入接受结构化数据的命令必须在 `--help` 或产品文档中明确声明该输入的格式与触发条件；管道输入与等价的 `--flag` 值输入必须产生相同的输出、退出码和副作用。

## 统一信封

每个 JSON 结果必须包含四个顶层字段：

| 字段 | 类型 | 规则 |
|---|---|---|
| `ok` | boolean | 命令是否成功 |
| `data` | object、array 或 null | 成功结果；失败时为 null |
| `error` | object 或 null | 失败信息；成功时为 null |
| `meta` | object | 契约版本和调用元数据 |

`meta` 至少包含：

- `schemaVersion`：字符串，初始值为 `1`。
- `command`：实际执行的稳定命令名称。
- `timestamp`：带明确时区的 ISO 8601 时间。

失败时，`error` 至少包含：

- `code`：稳定、机器可判断的大写错误码，格式为 `^[A-Z][A-Z0-9_]*$`。
- `message`：简短的人类可读说明，不包含敏感信息或不必要的本机路径。
- `details`：可选的结构化上下文；不得作为唯一错误标识。

## 一致性规则

- 成功时必须同时满足 `ok=true`、`error=null` 和退出码 `0`。
- 失败时必须同时满足 `ok=false`、`data=null` 和非零退出码。
- 同一种失败在不同调用中使用相同错误码。
- 调用方必须能够忽略未知字段；新增可选字段属于向后兼容变化。
- 删除字段、改变字段含义或改变类型属于不兼容契约变化。
- 人类默认输出可以更友好，但不得改变 `--json` 的行为。

## 示例

成功结果：

```json
{
  "ok": true,
  "data": {
    "id": "example-123"
  },
  "error": null,
  "meta": {
    "schemaVersion": "1",
    "command": "resource.get",
    "timestamp": "2026-07-22T08:00:00Z"
  }
}
```

资源不存在：

```json
{
  "ok": false,
  "data": null,
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "未找到请求的资源。",
    "details": {
      "id": "example-123"
    }
  },
  "meta": {
    "schemaVersion": "1",
    "command": "resource.get",
    "timestamp": "2026-07-22T08:00:00Z"
  }
}
```

该失败结果必须使用退出码 `3`。示例字段仅说明信封形状；下游项目必须使用自己的稳定命令名、错误码和无敏感信息的业务数据。

## 基础退出码

| 退出码 | 类别 |
|---|---|
| `0` | 成功 |
| `2` | 参数或输入无效 |
| `3` | 资源不存在 |
| `4` | 权限不足或操作未获批准 |
| `5` | 状态冲突或并发冲突 |
| `6` | 外部依赖不可用 |
| `10` | 业务操作执行失败 |
| `70` | 未分类内部错误 |

项目可以增加退出码，但必须记录含义，且不得重新定义以上类别。

## 契约验证

下游项目至少验证：

- 成功结果符合统一信封且退出码为 `0`。
- 一个最高风险失败结果符合统一错误结构且返回对应非零退出码。
- 标准输出可以被 JSON 解析器直接解析。
- 标准错误中的诊断不会污染标准输出。
- `--json` 不会等待交互输入。
- 输出是无 BOM 的 UTF-8 单一 JSON 文档，并能容忍末尾换行。
- `--help` 和 `--version` 或记录的等价入口能以预期状态只读退出。
- 破坏性操作缺少显式确认时拒绝执行，并返回权限或未获批准类别。

Rust 下游项目使用 `docs/RUST_CLI_TEMPLATE.md` 的默认实现与测试基线；其他语言必须提供等价行为和证据。
