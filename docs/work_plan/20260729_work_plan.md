# 当前工作计划

> 记忆日期：2026-07-29

## 目标

把已批准的发布构建前手动验收门禁固化为一致、可执行且可机械回归的 Harness 契约：日常开发和普通交付复核不自动触发 Computer Use E2E 等重型验收；构建/发布任务保留不可跳过的基础门禁，并让当次启用或硬要求的手动验收失败时可靠阻断打包。

- [x] 更新当日完整 Product Spec、Product Status、Work Plan，追加 ADR-20260729-003，并同步 AGENTS、README、工程规则、发布规则、Rust 基线摘要与 Changelog。

## 文件边界与实施顺序

1. **政策契约单元**：独占 AGENTS、README、当日 Product Spec/Status/Plan/ADR/Changelog、工程、验证、发布与必要 Rust 基线摘要；定义触发条件、执行顺序、阻断结果和可跳过边界，不修改 Skills、workflow 或 validator。
2. **Skills 单元**：独占相关 `.agents/skills/`；把“交付/发布自动 E2E”改为“构建前逐项询问、产物构建后打包前执行”，并让已启用或硬要求项目的非通过结果阻断。
3. **Workflow 与机械门禁单元**：独占候选 workflow、validator 和对应测试；先通过基础门禁，再按明确输入决定是否运行手动验收，最后才允许打包或后续发布动作。
4. **串行整合**：按政策、Skills、workflow/validator 顺序合入；解决语义冲突后运行开发门禁，并只把真实结果写入验证记录。

## 不包含

- 不在本轮运行 release build、最终产物 E2E、真实设备/外部环境验收、打包、产物收集、签名、上传、tag 或发布；本轮修改发布链路，但用户没有发起构建或发布准备。
- 不把编译、非空单元测试、相关集成/契约、最终产物存在性或只读启动冒烟改为可选，也不降低这些门禁失败时的阻断级别。
- 不自动启用手动验收，不跨任务继承选择，不允许在同一任务中通过取消已失败的选择绕过打包门禁。
- 不改变接口技术栈、Rust MSRV、许可证、版本、发布渠道、产品定价或商业化路线。

## 风险与回退

- 若触发条件仍把“普通交付复核”或“修改发布链路”当作 E2E 授权，开发流程仍会产生非预期重型操作；validator 必须覆盖这些反例。
- 若 workflow 在手动验收前已经打包、收集或签名，失败结果无法成为有效门禁；执行顺序必须是构建最终产物、手动验收、后续打包动作。
- 用户未启用的可选验收会留下真实环境风险；必须记录 `Not run`、原因与风险，产品/渠道硬要求不得进入可跳过分支。
- 手动验收可能失败、超时、被取消或选后未执行；四种状态都必须等价阻断当前任务，修复后重新执行并通过才可继续。
- 本轮采用独立 Worktree；各单元不得修改他人所有权文件，整合前逐个审查 commit 和差异，避免覆盖基线已有内容。

## 完成标准

- AGENTS、README、最新 Product Spec/Status/Plan、ADR、工程/验证/发布文档、相关 Skills、workflow 与 validator 对触发条件、当次选择、硬要求、执行顺序和阻断结果一致。
- 基础发布门禁始终运行且任何失败阻断打包；未启用且非硬要求的手动验收准确记录 `Not run` 与风险后可以继续。
- 已启用或硬要求的手动验收只在最终产物构建后、打包前执行；通过前不存在打包、上传、收集、签名或发布路径。
- 非空单元测试、Harness validator 与隔离负向回归全部通过；release build、真实 E2E、打包和人工复核如实记为 `Not run`，版本保持 `Unreleased`。
- 最终报告列出整合单元、实际检查、未执行发布动作、未验证平台/宿主与剩余风险。
