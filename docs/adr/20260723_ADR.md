# 2026-07-23 ADR

## ADR-20260723-005：Rust adapter 异步优先、GUI 无签名构建与统一 release 收集目录

- 日期：2026-07-23
- 状态：Accepted
- 关联需求：项目负责人要求 CLI、TUI、MCP、GUI 项目 Skills 使用基于 Tokio 的异步入口，开发默认优先异步，仅 CPU 密集型操作再考虑多线程；GUI 构建不强制签名；发布 Skill 将当前项目最新构建结果统一刷新到项目根 `release/`，收集前清理历史文件，并由初始化 Skill 把该目录写入 `.gitignore`。
- 背景：现有 Rust 基线虽统一 Tokio，却默认启用 `rt-multi-thread`，四类 adapter 对异步入口和 CPU 密集任务的边界强度不一致；GUI 构建未明确区分“无签名构建证据”与“目标渠道签名要求”；制品收集仍使用 `dist/v<version>/` 并保留历史候选，不符合统一、可刷新交付目录的要求。
- 决定：CLI、TUI、MCP 使用 Tokio current-thread 异步入口，GUI 复用 Tauri 提供的 Tokio-backed singleton runtime 并使用普通 `async fn` commands，不创建嵌套 runtime。I/O、等待、计时、进程、协议和界面命令默认沿 async 调用链；只有经测量确认的 CPU 密集工作才允许考虑 `spawn_blocking`、专用线程或多线程 runtime，并必须记录任务所有权、取消、并发上限、资源预算和验证。同步阻塞依赖必须替换为异步能力或进入范围/硬规则例外确认，不得静默用线程包裹。中性 bundled CLI 从 `rt-multi-thread` 改为 `rt` + current-thread。GUI 的本地构建、测试、产物存在和启动验证不得因缺少签名身份而阻断；商店、macOS 直接分发、Windows SmartScreen/Store、updater 等真实渠道仍按其独立签名要求阻断发布。`$collect-release-artifacts` 只写项目根 `release/`，在验证安全边界后先清空其历史内容，再从用户已完成的当前项目构建结果中复制与当前版本、源码 commit、构建 run、平台/架构声明一致的最新文件；歧义、碰撞、缺失或额外文件均阻断。初始化确保根 `.gitignore` 含 `/release/`。
- 影响范围：四类 adapter Skills 及其 baselines、Rust 技术基线、初始化 Skill 与 bundled asset、发布构建/收集/准备 Skills、`.gitignore`、产品规格、AGENTS/README、RELEASE、validator、状态、计划、验证和 Changelog。
- 不包含：不把 WEB adapter 改为 Rust Tokio 入口；不默认引入并行计算库或多线程 runtime；不替用户配置签名身份、证书、notarization、Store 或 updater；不授权发布、上传、tag 或 push；不从其他项目或旧版本复制制品。
- 理由：异步优先可避免等待型工作占用线程，current-thread 是不含 CPU 并行需求的最小 Tokio 默认；Tauri 官方暴露基于 Tokio 的 singleton async runtime 并建议 custom commands 使用普通 `async fn`。签名与构建是不同门槛，未指定分发渠道时不应让证书缺失阻断本地制品。单一刷新目录让用户总能找到本项目当前候选，同时避免历史文件混入。
- 风险：current-thread runtime 中混入阻塞或 CPU 密集任务会卡住整个 adapter；清理 `release/` 是有意的破坏性动作，路径解析错误可能删除越界文件；未签名 GUI 不能被误报为满足商店或 macOS 分发要求。通过 async/blocking 边界测试、严格 canonical root/symlink 门禁、只清理精确 `<project-root>/release`、先确定来源清单再清理、签名状态显式记录降低风险。
- 验证：运行受影响 Skill 快速校验、Python/Harness validator、bundled Rust asset 的格式/lint/测试/release build/冒烟，以及隔离 release 目录清理与最新文件选择测试；GUI/TUI/MCP 真实下游和签名渠道仍标记 `Unverified`。
- 恢复或调整标准：若真实性能证据证明 current-thread 不满足经批准的 workload，按测量结果记录 ADR 后启用最小多线程方案；若单一刷新目录妨碍审计，项目负责人可批准显式版本子目录，但必须同步清理、选择、忽略和验证契约。

## ADR-20260723-004：下游初始化以独立干净 Git 和空开发记忆收尾

- 日期：2026-07-23
- 状态：Accepted
- 关联需求：项目负责人要求初始化完成后验证下游项目是独立、干净的 Git 仓库，并要求初始化过程不迁移 ADR、Changelog、Product Spec、Work Plan，让这些内容在下游开发中自然产生。
- 背景：既有流程在独立 Git 中保留 unborn `HEAD` 和全部初始化文件为 untracked，不能满足 Git 对 clean worktree 的通常判定；同时它会复制四类目录索引并创建下游起始快照，使开发记忆在真实产品需求、计划或变化出现前就已存在。
- 决定：实例化完整排除 `docs/adr/`、`docs/changelog/`、`docs/product_spec/`、`docs/work_plan/`，不复制索引、日期正文或空占位。`$define-product` 在首项真实需求确认时创建 Product Spec 与 ADR，`$plan-change` 在首个真实计划时创建 Work Plan，`$implement-change` 在首次真实可见变更时创建 Changelog。Scaffold 验证和一次性裁剪完成后，初始化使用用户已有 Git 身份创建且只创建一个 `chore: initialize project` 本地基线 commit，并验证 top-level 精确等于项目根、分支为 `main`、`HEAD` 可解析、remote 为空、`git status --porcelain=v1 --untracked-files=all` 无输出。
- 影响范围：实例化与 Rust 初始化 Skills、对应 UI 元数据、产品定义/计划/实施 Skills、`AGENTS.md`、README、产品规格、Harness validator、项目状态、验证与 Changelog。
- 不包含：不自动配置或伪造 Git 身份，不修改全局 Git 配置，不创建 remote、push、tag、release 或签名；不把初始化基线 commit 当作产品实现或可发布 source commit；不删除直接初始化的既有下游项目记忆。
- 理由：空 porcelain 状态是可重复、无歧义的 clean 判据；本地基线 commit 让初始化结果可追溯且可继续开发。把四类记忆交给实际拥有它们的开发 Skill，可避免 Harness 历史和人为占位污染下游事实。
- 风险：缺少 Git 作者身份会使初始化在最终提交处阻断；基线 commit 改变了既有 no-auto-commit 语义；下游入口和 Skills 必须容忍四类目录初始不存在。通过拒绝伪造身份、明确唯一授权 commit、首次使用创建规则和 validator 回归门禁降低风险。
- 验证：运行 Skill 快速校验、Python 语法检查、Harness validator、当前描述扫描，并以隔离临时仓库验证独立 top-level、空 remote、基线 commit 与空 porcelain 的判定。真实 `$instantiate-project` 全流程和 Windows/Linux Git 行为仍标记 `Unverified`。
- 恢复或调整标准：若真实下游证明自动基线 commit 或延迟创建项目记忆不可接受，由项目负责人通过新 ADR 调整；必须同步初始化契约、拥有者 Skills、validator 和全部当前入口，不得用“已 init”冒充 clean。

## ADR-20260723-003：三类当前项目记忆改为按日完整快照

- 日期：2026-07-23
- 状态：Accepted
- 关联需求：项目负责人要求将 Product Spec、Product Status、Work Plan 拆入特定目录，使用 `YYYYMMDD_product_spec.md`、`YYYYMMDD_product_status.md`、`YYYYMMDD_work_plan.md` 命名；同日持续整理，新日从前一份综合撰写。
- 背景：三类当前事实原为 `docs/` 根目录固定单文件，无法像 ADR/Changelog 一样保留自然日边界；如果仅新建空白或增量文件，Agent 又会失去完整当前上下文。
- 决定：建立 `docs/product_spec/`、`docs/project_status/`、`docs/work_plan/`，各自用 `README.md` 记录规则和日期索引。日期正文使用小写 snake_case 后缀；同一自然日只更新同一文件。新自然日首次写入必须读取前一份，将仍有效事实、未完成事项与当日变化综合重写成完整当前快照。当前事实始终取各目录日期最新的文件，旧 `docs/PRODUCT_SPEC.md`、`docs/PROJECT_STATUS.md`、`docs/WORK_PLAN.md` 不保留兼容副本。
- 影响范围：三个项目记忆目录、`AGENTS.md`、README、工程规则、产品规格、相关项目 Skills、Harness validator、技术债入口、项目状态、验证与 Changelog。
- 不包含：不改变产品功能范围、接口选择、Rust/前端技术基线、ADR/Changelog/Verification/Technical Debt/Release 的存储模型，也不授权发布。
- 理由：目录索引保持稳定入口，日期正文保留每日边界；完整快照让 Agent 只需读取最新文件即可恢复当前事实，避免把多个增量文件错误拼接成当前规范。
- 风险：仓库外部对旧路径的引用会失效；索引未更新或“最新日期”选择错误会读取旧事实；新日只追加增量会造成上下文缺失。通过全仓原子迁移、索引规则和 validator 的命名/旧路径/关键语义门禁降低风险。
- 验证：运行 Python 语法检查、Harness validator、全仓旧路径扫描，并确认三个目录各有索引、合法日期正文、同日唯一与新日综合规则；文档结构变更不需要 Rust asset 重建，原因记录在验证中。
- 恢复或调整标准：若真实下游证明日期快照增加不可接受的维护成本，项目负责人可通过新 ADR 恢复单文件或采用其他索引；恢复必须同步全部入口与 validator，不能并存两套当前事实源。

## ADR-20260723-002：下游初始化能力一次性裁剪与首次开发门禁

- 日期：2026-07-23
- 状态：Accepted
- 关联需求：项目负责人要求生成后的下游抹除实例化/初始化 Skills、相关文档与门禁，禁止继续派生；`AGENTS.md` 永久保留 Skills/约束地图；开发环境检测独立保留；GUI/WEB 增加 Node.js 与 pnpm；GUI 首次开发补齐窗口与图标资料。
- 背景：当前下游完整继承 Harness 的实例化与初始化能力，环境脚本位于会被删除的初始化 Skill 内，Rust-only 项目也被无条件要求 Node.js，GUI 缺少首次开发前的人类应用身份和图标决策。
- 决定：初始化只允许完成一次。中性 scaffold 全部验证后，下游删除 `$instantiate-project`、`$initialize-rust-project`、模板 validator/方法论和活动初始化入口；保留独立 `$check-development-environment` 以及实际开发所需 Skills。模板和下游 `AGENTS.md` 均永久保留非空 Skills 地图与约束地图。Rust 始终门禁，Windows 保留 MSVC；仅 GUI/WEB 增加 Node.js 与 pnpm。GUI 首次真实开发前运行 `$prepare-gui-app-identity`，由用户在自动生成、确定性 Plan B、上传标准化/高清三条图标路径中选择。
- 影响范围：`AGENTS.md`、README、产品/Rust 基线、实例化/初始化/GUI/WEB Skills、新环境与 GUI identity Skills、门禁脚本/测试、validator、状态、计划、验证、技术债和 Changelog。
- 不包含：不在 Harness 根生成真实应用资料或图标；不执行真实下游裁剪；不验证未运行平台；不授权发布。
- 理由：终端下游不应继续携带模板复制能力；环境检测必须跨初始化生命周期存在并按真实接口最小化工具要求；GUI 人类可见身份应在人类确认后进入实现和打包。
- 风险：裁剪遗漏会保留派生入口，裁剪过早会破坏恢复；pnpm registry 或平台安装可能阻断；图标生成能力可能不可用。通过验证后裁剪、地图一致性检查、Plan B 与上传路径降低风险。
- 验证：Harness validator 检查 Skill 集、地图、裁剪契约与条件门禁；POSIX 隔离测试覆盖 Rust-only 不探测前端工具、GUI 已有工具、GUI 缺失安装、摘要失败与 MSRV 边界；Windows 保持静态契约检查并标记原生执行 `Unverified`。
- 恢复或调整标准：只有项目负责人通过新 ADR 才可改变终端下游边界、固定地图或条件工具链；普通下游不得自行恢复初始化 Skills。

## ADR-20260723-001：下游 Rust MSRV 提升到 1.90

- 日期：2026-07-23
- 状态：Accepted
- 关联需求：项目负责人要求“调整 MSRV 兼容到 rust1.90 及以上版本”。
- 背景：当前产品规格、初始化门禁、bundled Rust asset 和候选 workflow 统一声明 Rust 1.85；继续保留该下限会与新的兼容要求冲突。
- 决定：下游 Rust workspace 的最低支持版本统一改为 1.90.0，根 manifest 写入 `rust-version = "1.90"`；这是最低兼容声明而非精确版本锁。初始化门禁按版本顺序接受 stable Rust 1.90.0 及以上（包括更高的 1.x 与未来主版本），拒绝 1.89.x 及以下和预发布工具链；声明最低版本兼容时仍使用精确 Rust 1.90.0 工具链验证。本决定替代 ADR-20260722-002 中仅关于 MSRV 1.85 的部分，其余 Rust 2024、Tokio、shared core 和依赖边界继续有效。
- 影响范围：`docs/PRODUCT_SPEC.md`、`docs/RUST_CLI_TEMPLATE.md`、初始化 Skill 的门禁脚本/测试/bundled asset、候选 workflow、validator、发布检查、状态、技术债、验证和 Changelog。
- 不包含：不升级依赖、不改变 Rust edition 或架构、不发布制品、不把未运行平台改记为通过。
- 理由：以一个明确的最低版本统一生成项目、环境门禁和发布候选，避免文档声称 1.90 而实际资产或 CI 仍允许 1.85 的兼容性漂移。
- 风险：Rust 1.85 至 1.89 用户必须先升级工具链；固定 TUI/React 技术族仍需在真实下游重新解析兼容版本。
- 验证：隔离门禁证明 1.90.0、1.91.0、1.97.1 与 2.0.0 stable 通过且 1.89.0 被拒绝；Harness validator 检查版本事实；bundled asset 在当前 macOS 使用精确 Rust 1.90.0 完成 locked check、Clippy、非空测试、release build 和真实产物冒烟。
- 恢复或调整标准：若目标环境必须支持更低版本，由项目负责人确认新下限，并以新的 ADR、manifest/门禁/workflow 同步和精确工具链验证替代本决定。
