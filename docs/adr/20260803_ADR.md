# 2026-08-03 ADR

## ADR-20260803-003：开发流程改为风险分级的敏捷闭环

- 日期：2026-08-03
- 状态：Accepted
- 关联需求：项目负责人反馈现有流程固定步骤过长、浪费 Token 和时间，要求依据敏捷思想精简冗余步骤，并把适合的环节改为可选或用户选择。
- 背景：当前规则把范围确认、持久 Work Plan、Todo 状态机、非空单元测试、完整里程碑、Product Spec/Product Status/ADR/Verification/Changelog 同步和人工复核近似应用于所有改动。该模型能保护发布级交付，但对拼写修正、局部文档、低风险缺陷和可逆维护产生与风险无关的固定成本，也迫使 Agent 重复读取和重写大量快照。
- 决定：建立 `快速`、`标准`、`里程碑` 三条路径。用户可显式选择；未选择时 Agent 按范围清晰度、影响面、可逆性、外部副作用和交付目的自适应选择，并在实施前简短说明。安全/隐私、数据迁移、破坏性操作、凭据/生产/付费副作用、建立或改变对外兼容契约、渠道硬要求、签名/发布和跨平台最终候选必须进入里程碑路径，不能由用户选择降级；只修正文档对既有契约的描述不自动升档。
- 快速路径：低风险、局部、可逆且范围清楚的任务直接从用户请求或简短内联清单进入 `$implement-change`，不强制 `$define-product`、`$plan-change`、持久 Work Plan、ADR、Product Status、`docs/VERIFICATION.md` 或 `$verify-delivery`。只运行受影响的最小充分检查，并在最终回复概括证据。
- 标准路径：多步骤、多模块、需跨会话/交接、可安全并行或中等风险时使用 `$plan-change` 和精简 Todo。Product Spec 只在产品目标/边界/成功标准改变时更新；ADR 只记录长期重要、难以逆转或硬规则例外。真实交付目的或用户选择要求完整验收时，先升为里程碑，再调用 `$verify-delivery`。
- 里程碑路径：保留 Todo 完成门禁、真实候选、重新构建/测试、按风险或策略执行冒烟/E2E、失败回流和必要人工复核。只有该路径可产生里程碑已验收、候选 `ready` 或发布就绪结论。
- 验证分层：代码行为变更继续要求相关非空测试覆盖核心成功路径和最高风险失败路径；纯文档、元数据、格式与不可合理单测的机械变更可以直接采用链接、解析、静态校验、现有回归或差异检查，不再为测试数量单独建立 ADR 例外。任何路径都不得忽略真实失败。
- 记忆策略：Product Status 只在里程碑、重要阻断、跨会话交接或用户要求时更新；Work Plan 只在标准/里程碑路径或用户要求时创建；Verification 只保存里程碑、发布、人工复核或长期审计证据；Changelog 只记录用户或维护者可感知的真实变化。普通低风险检查不再触发整套日期快照联动。
- 初始化选择：保留现有四项 Agent 策略字段和模式定义。初始化先提供一次推荐敏捷预设，用户选择自定义时才逐项询问；最终仍不得遗留 `pending`。推荐预设为 Superpowers、并行 Worktree/Subagent 和适用冒烟 `enabled`，E2E `disabled`，其中 `enabled` 仍表示适用时采用而非无条件执行。
- 影响范围：README、AGENTS、当前 Product Spec/Status/Work Plan、工程与方法论文档、Agent 策略、规划/实施/验证/初始化等相关 Skills、Harness 校验器与测试、验证记录和当日变更记录。不改变独立 Git 根、许可证、接口技术栈、跨平台目标、发布/签名安全边界或外部授权要求。
- 理由：敏捷的核心是缩短反馈循环、减少在制品和按风险投入证据，而不是取消质量。三条路径让大多数日常改动走最短可靠闭环，同时把高成本门禁集中到它们真正降低风险的场景。
- 风险：Agent 可能低估任务风险或把多个小改动拼成未规划的大变更；可选记忆可能降低跨会话可恢复性；预设可能不符合个别团队偏好。通过明确升级触发器、用户随时升档、标准路径的交接计划和里程碑硬门禁缓解。
- 验证：更新机械检查以接受快速路径无持久计划、拒绝里程碑在未完成 Todo 下通过，并覆盖初始化预设/自定义两条分支；运行相关非空校验器回归、20 个 Skill 结构检查、`python3 scripts/validate_harness.py`、链接/语法和 `git diff --check`。本轮不运行冒烟/E2E，不产生发布候选。
- 恢复或调整标准：若真实下游显示快速路径持续漏掉高风险变更，则收紧可判定的升级条件；若某类持久记录对交接价值显著高于成本，将该类任务提升为标准路径，而不恢复所有任务统一走完整流程。

## ADR-20260803-002：文档与项目 Skills 的英文自然语言统一翻译为中文

- 日期：2026-08-03
- 状态：Accepted
- 关联需求：项目负责人要求把现有 `docs/` 与 `.agents/skills/` 中的英文部分全部改为中文。
- 背景：当前 `docs/` 主体已经使用中文，但仍有英文标题和面向读者的展示词；项目 Skills 的文件头元数据说明、工作流、边界、参考文档与 `agents/openai.yaml` 元数据仍以英文自然语言为主，导致 Agent 和维护者需要在中英文之间切换。
- 决定：翻译 `docs/` 与 `.agents/skills/` 内所有面向读者或 Agent 的英文自然语言，包括标题、说明、步骤、边界、注释、文档链接文字和工作流的人类可读标签。为保持程序、协议和验证稳定，Skill 名称、命令、路径、文件名、代码、配置键、JSON/清单字段、枚举与固定状态值、测试标识符、版本、哈希、第三方产品名和通用技术缩写保持原样；必要时在中文语境中保留这些精确词元。
- 影响范围：`docs/` 全部文本文件与 `.agents/skills/` 中的 Skill 说明、参考、元数据及可安全本地化的人类可读资产；因脚本输出字面量变化而必须同步的根校验器和回归测试也纳入本次维护。不修改根 `README.md`、`AGENTS.md`、许可证、产品业务边界、外部系统或发布状态。
- 理由：完整中文说明能降低下游初始化、规划、实现、验证和发布维护中的理解成本，同时保留机器词元可避免本地化破坏契约、脚本和既有验证。
- 风险：把机器匹配词误译会使校验器、工作流或下游命令失效；遗漏嵌在模板或资产中的英文会造成翻译不完整；历史记录中的固定事实值不能因语言转换被改写。
- 验证：运行英文自然语言残留扫描并逐项分类，校验 20 个项目 Skills 的结构，执行 `python3 scripts/validate_harness.py`、相关现有单元/回归、YAML/脚本语法检查和 `git diff --check`。本次不改变运行时代码逻辑，因此非空单元测试要求采用文档/Skill 变更例外，以现有校验器与结构化残留扫描作为替代验证；不得运行冒烟或 E2E。
- 恢复或调整标准：若下游工具要求某段英文作为精确机器输入，恢复该最小词元并在中文上下文说明；不得因此恢复整段英文自然语言。产品规格的目标与范围不变；产品状态、工作计划、验证记录与变更记录需同步记录本次维护流程变更。

## ADR-20260803-001：Rust CLI 构建默认三平台、条件签名并直接刷新根发布目录

- 日期：2026-08-03
- 状态：Accepted
- 关联需求：项目负责人要求构建在条件存在时尝试签名，默认全平台构建、不满足时回退当前平台，并在构建前清空项目根 `release/`、构建后把结果放入该目录；初始化必须忽略该目录。
- 背景：现有 `$build-rust-release` 只构建当前宿主且明确禁止签名；三平台工作流需显式选择并输出到 CI `dist/`；`release/` 只在里程碑验收通过后的收集阶段刷新。这三点均与已确认需求冲突。
- 决定：`$build-rust-release` 成为 Rust CLI 候选编排入口。默认先预检并派发 Windows、macOS、Linux 原生矩阵；只有提供方、权限、三类运行器或结果取回能力在派发前不可用才回退当前平台。矩阵启动后的失败、超时或取消保留为真实失败，不得以回退掩盖；矩阵采用 `fail-fast: false` 收集终态。远端工作流必须用必填 40 位 `source_commit` 检出并复核批准源码，关闭检出凭据持久化。
- 发布语义：初始化继续使根 `.gitignore` 精确一次包含 `/release/`。每次构建在任何格式、测试或构建命令前调用跨平台辅助程序，验证规范化的独立 Git 根目录，拒绝符号链接/重解析点、非目录与路径越界，把旧目录原子移入同文件系统隔离位置，创建并复核全新空目录，再只删除隔离旧树；不得通过活动目标目录原地递归删除。签名后的归档/校验和/清单先在同根唯一暂存区中形成精确普通文件集，再通过不跟随链接的目录级原子重命名，将完整暂存区提交为 `release/`；每个平台只上传这三个精确路径；允许 `milestoneAcceptance: pending`，目录存在不等于 `ready`。
- 签名语义：项目已有批准的非交互钩子/命令、工具和已授权凭据时，在归档/哈希前尝试签名并验证；尝试失败使对应平台构建失败，不得静默回退 `unsigned`。条件不全时记录 `signingStatus: unsigned` 和原因，只有产品/渠道硬要求才阻断。清单同时记录 `signingReason` 和结构化 `signingEvidence`；默认原地钩子记录验证成功且没有分离文件。构建不创建、索取、导出、输出或上传凭据，也不自动执行公证。
- 验收边界：签名后的最终候选字节进入 `$verify-delivery`。验收后再次改变字节或运行行为的签名、公证、重打包属于新候选，必须重新验收。构建、收集和发布准备仍不运行冒烟/E2E；标签、正式发布和发布上传未获授权。
- 适用范围：当前统一原生矩阵仅覆盖 `$build-rust-release` 已定义的 Rust CLI 产物模型。TUI、MCP、GUI 继续使用适配器特有的产物规则，跨接口统一矩阵仍由 LIM-015 跟踪。
- 替代关系：本决定替代 ADR-20260723-005 中“只在 `accepted` 收集时清理 `release/`”和“构建完全不尝试产品签名”的部分；保留其规范化根目录/符号链接安全边界、`unsigned` 不等于渠道 `ready`、以及不自动配置签名身份的决定。
- 理由：全平台优先使默认交付目标与 Windows/macOS/Linux 一致；严格区分预检不可用与真实构建失败可防止本机成功掩盖平台回归；在构建前清理并以清单区分 `pending`/`ready`，既满足固定结果路径，又避免目录存在被误报为已验收。
- 风险：`release/` 清理是有意的破坏性动作；签名钩子可能错误探测凭据或泄露输出；远端运行器的项目根与调用方本地根不同；当前工作流仍仅支持 CLI，且尚未在真实 GitHub 运行器或真实签名环境前向验证。
- 验证：新增 POSIX/PowerShell 辅助程序、原子刷新与符号链接/Git 边界回归、精确 `.gitignore` 门禁、工作流全文件摘要与步骤顺序检查，以及全平台路由、源码提交固定、`fail-fast: false`、条件签名/证据、精确传输文件集的正负向测试。Windows PowerShell 的运行用例在有 `pwsh` 的宿主执行；当前 macOS 无 `pwsh` 时明确跳过。真实三平台运行器与真实产品签名保持 `Unverified`，不得由静态测试推断通过。
- 恢复或调整标准：若真实项目证明自动签名探测不可靠，保持清单与验收边界并退回显式的固定签名配置；若三平台提供方长期不可用，可记录批准的目标矩阵调整，但不得把已启动平台失败重新定义为回退条件。
- 文档同步：新建 2026-08-03 产品规格、产品状态与工作计划完整快照，并同步 README、AGENTS、工程/Rust/发布规则、Skills、校验器、验证记录、技术债与变更记录。
