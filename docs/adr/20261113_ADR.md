# 2026-11-13 ADR

## ADR-20261113-001：下游按次选择 Release 或 Beta

- 日期：2026-11-13。状态：Accepted。变更标识 `HARNESS-RELEASE-CHANNELS`，`required_version = pending`。
- 确认来源：负责人要求将下游开发阶段明确为 dev，并在下游发布时选择 Release 或 Beta。
- 决定：仅在下游的新发布上下文中冻结渠道；推送、打包和候选复核由同一个上下文派生渠道。Beta 应用名称与标题加 Beta 后缀，应用 ID 加 `.beta`，远端渠道分支为 `beta`。构建进程以 `HARNESS_RELEASE_CHANNEL` 区分阶段。
- 兼容：延续本地默认主分支、版本与 tag 契约，Harness 源沿用 schema 3 和固定的 `release` 分支。旧下游 schema 3 以原摘要按 Release 读取。Release 和 Beta 都延续发布后同步远端默认主分支的流程；默认分支若是另一渠道则拒绝推送。
- 风险与验证：用独立 Git 仓库覆盖渠道绑定、分支隔离和旧摘要读取，桌面打包配置通过开发回归。真实平台安装和签名仍以各项目候选验证为准。渠道契约和调整入口见 [发布渠道](../RELEASE.md#发布渠道)。

本快照承接仍有效的决定与历史版本绑定。退役接口的完整决定见[历史归档](ADR_history.md)。旧决定中与已退役路径相关的描述记录其当时范围。

## ADR-20261108-004：发布后本地候选目标与 NSH 批次边界

- 日期：2026-11-08；状态：Accepted；变更标识：`HARNESS-CHANGE-DETERMINISTIC-LOCAL-PACKAGE-ROUTE`；`required_version = 202611081358`，仅正式发布时取 Harness 时间版本。
- 确认来源：负责人要求梳理整个 Harness，使语义清晰且工作流稳定一致；现行发布规则与单目标构建 helper、NSH 批次目录存在可复现的执行冲突。
- 背景：`local_package` 只写“适用打包 Skill”，CLI 与桌面组合或 NSH 多目标下无法确定本次构建目标；通用规则又要求整个 `release/` 为当前构建，而 NSH 构建器按目标保留多批次，旧批次会与验收的全目录同 HEAD/同状态要求冲突。
- 决定：已冻结的 `postReleaseAction = local_package` 授权在当前宿主生成并校验一个已选接口及目标的正式本地候选；目标按受管只读路由确定，候选可保持 `pending`，其他接口和平台须另行构建与验收。若本机无可用目标或目标构建失败，只报告 Git 发布已完成、后续动作受阻，不自动切换目标。NSH 候选保留独立目标批次；完整验收只针对明确选定、绑定当前发布 HEAD 与上下文的一个批次，原子更新该批次，旧批次不参与本次同状态判定。含 TUI 的 NSH 与受跟踪锁无法传递到运行时工作区的 NSH 仍不得选择发布后本地打包。
- 取代范围：取代“所有候选每次都刷新整个 `release/`”对 NSH 的适用，以及发布后本地打包目标由 Agent 临时猜测的空白。扁平候选仍按现有整目录原子替换；既有已发布 HEAD 下的合法候选不因新目标路由被追溯否定，已初始化下游的 Cargo 平台和已冻结发布动作不改写。
- 理由与影响：单宿主构建器每次只能形成可观察的一个候选目标；按目标隔离历史批次可保留来源和拒绝证据，验收不再让其他批次污染当前结论。完成一次本地打包不代表全部目标可运行、完整验收通过或渠道就绪。
- 风险与验证：固定目标顺序可能与当前产品优先级不同，其他目标须由明确的独立候选请求覆盖；受管路由需用 CLI＋GUI、NSH 多目标和不可构建宿主矩阵回归，批次验收需复核选定批次的精确文件集、上下文和原子状态写入；真实产品候选、跨宿主运行及签名不由 Harness 文档测试代替。
- 恢复或调整标准：若需一次发布后形成多个目标候选，先明确目标集合、跨宿主来源和整组原子验收机制，再修改发布动作、构建器、manifest 与回归；不得把历史批次或 `pending` 状态解释为额外目标已通过。

## ADR-20261108-003：初始化逐项询问与可点击多选确认

- 日期：2026-11-08；状态：Accepted；变更标识：`HARNESS-CHANGE-SEQUENTIAL-INITIALIZATION-QUESTIONS`；`required_version = 202611081358`，仅正式发布时取 Harness 时间版本。
- 确认来源：负责人要求首次表单及后续问询统一逐项进行，使支持多选的程序类型和 NSH 能力可勾选并由用户确认，而非要求用户手打选项。
- 背景：既有解析器在 `base` 阶段一次返回全部未答基础字段，条件字段才一轮一个；目录虽列出多选枚举，但没有交互控件类型，Agent 容易把多选题写成需自行输入的文本清单。
- 决定：初始化每轮仅返回一个待补或待修正字段，其他结构化补问也每轮只呈现一个待决字段；已提前明确的合法字段仍直接复用，缺少的第二展示名仍自动翻译。空表单先问中文名时提供可点击的“改用英文名”，跳过中文名后只问英文名；两种语言都跳过时重新问名称。问句目录标明文本、单选或多选；有宿主交互工具时，选项均由用户点击，多选优先同一复选控件勾选多项后确认。宿主只有单选控件时，每个选项逐项点击选择/不选择，展示所选集合并由用户点击确认后才写入数组；没有可点击工具且未获明确答案时如实说明限制，不让用户手打枚举值或伪称已经展示复选框。最新完整汇总继续单独显式确认并绑定摘要。
- 取代范围：取代 ADR-20260828-002 与 ADR-20261108-001 中“首轮集中列出全部基础字段”的问法；保留其字段顺序、合法预填复用、路径校验和写入前完整汇总确认。ADR-20261108-002 的平台默认与 NSH 派生规则不变；既有下游配置不追溯改写。
- 理由与影响：每轮一个字段使当前选择和错误修正明确；多选在具备控件的宿主可一次勾选确认，在仅有单选工具的宿主以更多次点击保留无手打选项的交互。问句目录与解析器不能自行创建宿主原生复选控件，因此不把 schema 标记误报为已展示的真实 UI。
- 风险与验证：回归需覆盖基础字段顺序、预填与非法值逐项修正、多选数组归一和问句控件模式，并运行 Harness 合同校验；真实宿主复选控件是否可用须按当次工具能力判断，模拟问句不能代替实际 UI 证据。
- 恢复或调整标准：若宿主新增原生多选工具，直接按同一目录启用复选路径；若逐项点击造成实际阻断，先确认可用交互工具，再修改唯一合同与相关回归，不回退为要求用户手打枚举值。

## ADR-20261108-002：取消系统平台问题并从 NSH 能力派生平台

- 日期：2026-11-08；状态：Accepted；变更标识：`HARNESS-CHANGE-SIMPLIFIED-INITIALIZATION-FORM`；`required_version = 202611081358`，仅正式发布时取 Harness 时间版本。
- 确认来源：负责人指出 NSH 初始化连续询问系统平台和 NSH 能力，要求只保留 NSH 能力问题；随后明确要求 Windows/macOS/Linux 系统平台彻底不问，默认支持全部平台。
- 背景：既有表单把 `target_platforms` 固定为程序类型后的必答问题，选择 NSH 后又要求 `nsh_targets`，两个答案描述重叠的平台范围。该问法来自解析器、问句目录及上一条 ADR 的共同设计，不是偶发的模型重复发问。
- 决定：初始化表单删除系统平台问句。CLI/MCP/DESKTOP 统一派生 `windows, macos, linux`，来源 `default:all_desktop_platforms`；NSH 只询问 `desktop, mobile, web, tui` 能力，桌面或 TUI 派生完整 Windows/macOS/Linux，移动派生 Android/iOS，Web 派生 Web，共用平台去重并记录来源 `derived:nsh_targets`。派生平台与能力在写入前的完整汇总中显示并由用户确认；根 Cargo 仍保存非空 `target-platforms` 和适用的 `nsh-targets`。旧表单已输入的平台值只供会话兼容读取，不再改变新项目范围。DESKTOP 框架和桌面条件能力的问询仍按所选路径执行。
- 取代范围：取代 ADR-20261108-001 中“程序类型后单问目标平台”的子句，以及 ADR-20261107-004 中新 NSH TUI 可只选部分桌面系统的初始化选择方式；TUI 运行时及预览路线随后由 ADR-20261108-005 暂停。其余接口组合、固定策略和发布动作继续有效。已初始化下游的受保护 Cargo、profile 和用户选择不追溯改写。
- 理由与影响：一次能力选择即可确定 NSH 平台，其他接口无需重复选择固定三系统，减少初始化问询。默认平台声明覆盖全部对应系统，但不表示已经在各宿主构建、运行或验收；GPUI 含 Linux 时托盘与全局快捷键等现有限制继续按能力门禁显示。若仅需某系统的新项目，当前表单不提供缩小平台范围的选项，须另行确认并调整合同。
- 风险与验证：防止旧平台答案覆盖新默认、NSH 桌面与 TUI 重复系统、非 NSH 出现 Android/iOS/Web、旧确认摘要复用，以及把平台声明误报为实际验证；运行表单定向回归和 Harness 门禁。真实下游及跨平台宿主运行仍须独立取证。
- 恢复或调整标准：若全平台默认与真实项目需求冲突，先确认新的平台选择范围，再修订唯一表单、Cargo 写入和相关回归；不得静默回退为两轮 NSH 问询或改写已初始化下游。

## ADR-20261108-001：分轮确认初始化类型与平台并延后发布动作

- 日期：2026-11-08；状态：Accepted；变更标识：`HARNESS-CHANGE-SIMPLIFIED-INITIALIZATION-FORM`；`required_version = 202611081358`，仅正式发布时取 Harness 时间版本。
- 确认来源：负责人要求简化九项基础表单，并明确补充“DESKTOP 可与 CLI/MCP 组合，但不能与 NSH 组合”。
- 背景：原首轮同时询问目标平台、程序类型、Agent 策略模式和未来发布后动作；目标平台与动作的适用范围依赖程序类型，固定推荐值又使策略模式问题增加无必要的选择。
- 决定：首轮只收集中英文展示名（至少一个由用户提供）、ASCII `snake_case` 标识、项目路径、负责人和程序类型。程序类型确定后单问目标平台；CLI、MCP 可互相组合，也可与 DESKTOP 组合，NSH 只能单选。六项 Agent 策略固定物化为自动 Task、Task 工作树、superpowers、内部并行关闭，候选冒烟允许，候选 E2E 建议关闭；初始化不问策略模式或单项能力。新下游 schema 5 保留 `post_release_action: pending`，首次发布前呈现本地打包与提交远程并记录明确选择，未选时发布失败关闭。既有下游已确认的策略与发布动作不改写，后续明确变更仍走各自专用 Skill。
- 取代范围：部分取代 ADR-20260828-002 对首轮平台和策略模式同问的要求、ADR-20260928-003 对初始化时选择发布后动作的要求，以及 ADR-20261010-002 和 ADR-20260917-001 对新项目推荐/自定义策略问询的要求；这些决定的字段语义、已确认下游偏好、发布动作冻结与执行、Task 环境边界继续有效。NSH 子目标和桌面九字段条件问询不变。
- 理由与影响：后续问题只展示已选程序类型适用的选项，减少创建时需要决策的字段；表单解析、schema 5 策略读取、首次发布动作门禁、实例化裁剪、活动文档和验证器须同步。
- 风险与验证：重点防止隐式附加 CLI、平台选项越界、`pending` 错误阻断中性基线或穿过发布门禁，以及旧 schema 行为回退。以表单、实例化、动作选择、生命周期和 Harness 门禁回归验证工程合同；真实下游实例化与首次发布尚未前向验证。
- 恢复或调整标准：若真实下游问询或首发流程发现缺口，先复核持久接口、平台、策略和发布事实，再修正表单与门禁并重跑相关回归；不得静默改写既有下游选择或跳过首发确认。

## ADR-20261107-003：新 NSH 桌面使用 Mixed 界面与条件原生宿主

- 日期：2026-11-07；状态：Accepted；变更标识：`HARNESS-FEAT-NSH-MIXED-DESKTOP`；`required_version = 202611071119`，仅正式发布时取 Harness 时间版本。
- 确认来源：负责人要求重新参照本机 `nsh-desktop` 示例完善 NSH 桌面接线与知识库，明确指定“TsxUI + Rust业务，创建时使用Mixed模式”，多窗口默认支持，托盘、单实例、深链接、自启等能力像 Tauri/GPUI 逐项询问；另确认本轮系统通知和 OS 全局快捷键继续不可用，并批准生成下游所需的按平台最小声明的项目本地依赖。
- 决定：新顶层 NSH 的 TSX UI 通过 Mixed 原生模块调用共享 Rust core；桌面目标生成自定义 AppKit、Win32、GTK 宿主并固定支持多窗口。统一九字段 profile 仅对桌面询问；托盘、自启、单实例、深链接按明确选择生成和验证，深链接依赖单实例。系统通知与 OS 全局快捷键必须 `disabled`，应用内快捷键不能冒充 OS 热键。移动和 Web 继续使用 NSH 官方 Mixed runner，不接受桌面 profile；TUI 仍失败关闭。
- 打包与兼容：新顶层 NSH 桌面由 Mixed bundle、Cargo 宿主和平台资源组成，不能用官方单窗口 `nsh package` 冒充自定义宿主包。macOS URL scheme 随 app 声明；Windows/Linux 的注册脚本随包交付且只在深链接启用时生成。旧 `interfaces = ["gui"]`、`gui-framework = "nsh"` 工程保持只读兼容，不自动覆盖既有下游产品源码、身份或 profile。
- 取代范围：取代 ADR-20261106-001 对新 NSH 的“Rust UI”及六项桌面宿主能力一律不可用的子句，以及 ADR-20261107-002 对这六项不可用边界的继承；两项仍不可用。共享 core、目标平台选择、旧工程保护、固定 0.4.0、锁策略和平台独立取证继续生效。
- 理由与风险：示例采用 TSX 与自定义宿主，官方 `nsh package` 的桌面 runner 不包含该宿主，原 Rust UI 无示例所用的 `host.call` 桥接。跨平台宿主行为、OS 注册、进程恢复和签名均须在目标原生系统验证，源生成器与 mock 渲染测试不能替代实际运行。新增的第三方依赖只进入所需平台的下游 Cargo 声明；生成器仍使用 Node 标准库。

## ADR-20261107-002：NSH 独立为顶层程序类型并按目标选择能力

- 日期：2026-11-07；状态：Accepted；变更标识：`HARNESS-CHANGE-NSH-TOP-LEVEL`；`required_version = 202611071119`，仅正式发布时取 Harness 时间版本。
- 确认来源：负责人明确要求“将NSH从Desktop中移动出来，与CLI MCP DESKTOP 平齐”，说明改为“下一代全平台开发框架”，在 NSH 下选择桌面、移动、Web、TUI，并将现有 NSH 能力移到其桌面能力下。
- 背景与决定：新初始化表单把 NSH 作为独立程序类型；新工程在根 Cargo 写 `interfaces = ["nsh"]`、`nsh-targets` 和具体 `target-platforms`，适配器成员使用 `_nsh`，不写 `gui-framework`。DESKTOP 保留 Cargo `gui` 与 Tauri/GPUI 框架选择。现有 NSH 九字段能力只在选中桌面子目标时询问并记录；移动和 Web 不继承桌面 profile。

- 取代范围：取代 ADR-20261106-001 的“NSH 是第三个 GUI 框架”、所有 NSH 九字段无条件适用及按 `gui-framework` 路由新项目的部分；其运行时、共享 core、打包和真实验证边界保留。ADR-20261107-001 的 TUI 移除边界明确限于独立顶层 Ratatui 程序类型；本决定新增的 NSH TUI 子选项仍不可生成工程，不恢复旧适配器。

- 恢复或调整标准：若目标分类或兼容性出错，修订表单、生成器及读取端并重测，保护既有下游文件；开放 TUI 前须有固定 runtime 的实际 API、可运行与可打包产物及对应 E2E，不从旧独立 TUI 适配器回填。
