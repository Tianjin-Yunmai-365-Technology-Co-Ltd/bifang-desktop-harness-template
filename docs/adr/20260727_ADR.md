# 2026-07-27 ADR

## ADR-20260727-003：Harness 版本事实文件与 1.0.0 初始版本

- 日期：2026-07-27
- 状态：Accepted
- 关联需求：项目负责人要求审计所有文档、修复冲突与残留，新增 `Version.md`，将初始版本设为 `1.0.0`，并在验证后提交、推送。
- 背景：当前 README、Product Spec 与 `docs/RELEASE.md` 把 Harness 版本摘要为 `0.1.0`，且 `docs/RELEASE.md` 同时承担当前版本事实和发布规则；仓库没有用户要求的独立版本文件。直接复制该文件到 Rust 下游又会与根 `Cargo.toml` 的版本事实冲突。
- 决定：在 Harness 根目录新增 `Version.md`，把当前版本、初始版本和发布状态统一记录为 `1.0.0`、`1.0.0`、`Unreleased`，并将其设为 Harness 版本事实的唯一来源。`docs/RELEASE.md` 继续作为 Semantic Versioning 和发布门禁来源，只链接并摘要 `Version.md`。`$prepare-release` 必须读取该文件；`$instantiate-project` 必须排除 Harness 专用的 `Version.md`，让初始化后的 Rust 下游继续只以根 `Cargo.toml` 为版本事实来源。历史 Product Spec、ADR、Changelog 和验证记录中的 `0.1.0` 作为当时事实保留，不批量改写。
- 影响范围：根 `Version.md`、README、AGENTS、当前 Product Spec、Product Status、Work Plan、工程规则、方法论文档、发布规则、相关 Skills、validator、验证、技术债和 Changelog；全部 Markdown 文档同时接受链接、当前事实、旧身份、已替代规则和本机路径残留审计。
- 不包含：不改变 bundled Rust 下游初始版本 `0.1.0`，不把当前未发布变更伪装成正式发布，不创建 tag、发布物或 GitHub Release，不改写历史验证证据。
- 理由：独立短文件让 Agent 和维护者快速获得版本事实，同时把易变版本值与较长发布规则分离；显式排除下游复制可避免两个版本事实源。
- 风险：新增事实源可能遗漏同步位置，或被错误复制到下游；通过 validator 的必需文件、精确内容、当前摘要一致性和实例化排除契约检查降低风险。推送会改变远端共享分支，但已由本需求明确授权，并在提交前执行最终 diff 和 remote/branch 复核。
- 验证：运行全部 Markdown 链接与当前事实扫描、项目 Skills 结构校验、`python3 -m py_compile scripts/validate_harness.py`、`python3 scripts/validate_harness.py`，并执行与 Harness bundled asset 相称的检查；实际结果写入 `docs/VERIFICATION.md`。提交和推送成功后记录分支、commit 与 remote 结果。
- 恢复或调整标准：若未来 Harness 需要机器可读 manifest，可由新 ADR 指定受控同步或迁移方案；在此之前不得重新把 `docs/RELEASE.md` 或其他摘要设为并列事实来源。若下游改用非 Rust 技术栈，其版本事实来源须在下游范围确认中单独指定，不能默认继承 Harness `Version.md`。

## ADR-20260727-001：企业专有商业许可与终端下游许可证继承

- 日期：2026-07-27
- 状态：Accepted
- 关联需求：项目负责人确认本企业项目及其收费下游不采用开源协议，要求生成中英文两份 License，保护项目和项目知识产权，并在派生下游项目时一起复制；下游项目禁止继续衍生。
- 背景：现有 Harness 通过一次性初始化裁剪实现工程层面的终端下游，但没有法律文本限制客户复制、修改、转售、再许可或继续派生。开源许可证必须允许修改和衍生，不符合本项目边界；普通 `All Rights Reserved` 声明又不足以约定付费授权、源码交付、终止和商业文件关系。
- 决定：采用自定义的非开源企业专有商业软件许可，根目录分别保存 `LICENSE.zh-CN.md` 与 `LICENSE.en.md`。两种语言表达同一条款，冲突时中文优先；具体许可方、被许可方、费用、期限、数量和特殊授权由双方签署的商业文件确定，商业文件只对其明确处理的冲突事项优先。许可覆盖包含文件的项目及交付的源码、目标代码、配置、Skills、脚本、模板、工作流、资产、文档、设计和更新，但保留第三方材料各自许可证。下游是终端项目，不得作为 Harness、模板、脚手架、SDK、代码生成器、产品底座或其他重复派生能力。`$instantiate-project` 必须逐字节复制两份文件；`$initialize-rust-project` 裁剪时必须保留并验证两份文件存在且未更改。
- 影响范围：根许可证、README、AGENTS、产品规格、状态、计划、实例化/初始化 Skills、RELEASE、validator、验证和 Changelog。
- 不包含：不确定真实交易变量，不把通用文本作为已签客户合同，不替代专业法律意见，不修改第三方许可证，不授权发布。
- 理由：专有商业许可同时支持收费、有限内部使用、源码可见但权利受限和禁止二次派生；将交易变量放入商业文件可让同一仓库文本稳定继承到不同下游，而不在模板中虚构客户信息。
- 风险：条款可能受具体司法辖区强制性法律限制；客户可能要求 OEM、集团共享、源码 escrow 或更宽维护权；第三方依赖可能带来额外通知或源码义务。通过法务复核、商业文件显式授权、第三方许可证审计和禁止隐式例外降低风险。
- 验证：运行 `python3 -m py_compile scripts/validate_harness.py`、`python3 scripts/validate_harness.py`，并在隔离副本分别删除许可证和关键禁止衍生条款，确认 validator 非零退出。真实下游逐字节复制与正式合同效力保持 `Unverified`，在首个收费下游和真实客户合同中复核。
- 恢复或调整标准：若商业模式改为开源、双重许可、OEM 或允许受控二次派生，必须由项目负责人通过新 ADR 明确授权范围，并经法务复核后同步两份许可证、实例化门禁、产品规格和发布要求；不得只修改其中一种语言或单个下游文件。

## ADR-20260727-002：派生下游全量项目身份改名

- 日期：2026-07-27
- 状态：Accepted
- 关联需求：项目负责人要求检查派生下游时文档、Skills 和 Licenses 是否都强制改为目标项目名，并新增可快速修改所有项目产品名前缀配置、Skills 与 Licenses 名称的全量改名 Skill。
- 现状结论：旧契约只明确重写 README 与保留项目记忆并搜索残留 Harness 身份；Rust asset 的 `example_tool` 由初始化流程处理，但没有统一、可执行的全仓改名门禁。ADR-20260727-001 同时要求两份许可证逐字节复制且身份重置不得改写，因此许可证不会显示目标项目名。结论是“未全部强制”。
- 决定：新增并在下游保留 `$rename-project-identity`。它接受旧/新展示名、ASCII `snake_case` 标识、kebab-case 前缀及额外精确映射，默认只输出 JSON 预览，显式 `--apply` 后统一修改项目自有文本和路径；覆盖配置、源码、文档、Skills 与两份 License 的适用项目名，并阻断路径覆盖、符号链接和旧身份残留。`$instantiate-project` 先原样复制 License，再只替换两个双语项目名 token；其余法律条款必须保持不变。该精确身份替换是对 ADR-20260727-001“身份重置不得改写许可证”的局部替代，不改变其专有许可、终端下游和其他法律决定。
- 影响范围：根 Licenses、实例化/初始化 Skills、新改名 Skill、README、AGENTS、Product Spec、Product Status、Work Plan、RELEASE、validator、验证与 Changelog。
- 不包含：不改第三方或生成内容，不自动猜测缩写/应用 ID，不改变产品范围、版本、法律主体、许可权利、发布授权或历史验证事实。
- 风险：全仓替换可能误改历史证据、第三方声明或目标路径；许可证命名变化也可能被误解为条款变化。通过维护树排除、预览、精确映射、碰撞/符号链接阻断、应用后残留扫描、双语项目名对照和 diff 复核降低风险。
- 验证：运行 Skill 隔离单元测试、`quick_validate.py`、Python 语法检查、Harness validator，并在隔离目录验证成功改名、目标碰撞和符号链接失败。真实完整下游改名仍为 `Unverified`。
- 恢复或调整标准：若真实下游出现无法由精确映射表达的标识体系，先扩展输入与测试；不得改成无预览的模糊搜索替换，也不得为清零残留而扫描或修改第三方、生成物和 Git 内部数据。
