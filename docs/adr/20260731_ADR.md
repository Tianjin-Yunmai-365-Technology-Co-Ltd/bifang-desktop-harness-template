# 2026-07-31 ADR

## ADR-20260731-004：下游项目一次持久化 Agent 策略并按适用性自主决策

- 日期：2026-07-31
- 状态：Accepted
- 关联需求：下游项目只询问一次是否启用 Superpowers、Worktree/Subagent、冒烟和 E2E，随后固化并允许 Agent 自主参考，无法判断时再询问。
- 背景：当前只有 Superpowers 持久化；Worktree/Subagent 与 E2E 按任务重新询问，冒烟没有用户开关，造成重复打断和跨会话不一致。
- 决定：扩展 `docs/AGENT_POLICY.md` 为可解析的唯一项目策略源，分别记录 `superpowers`、`parallel_worktree_subagents`、`milestone_smoke`、`milestone_e2e`。下游初始化前四项必须由用户确认并写为 `enabled`/`disabled`；Harness 源和初始化中状态可为 `pending`，但初始化基线提交禁止残留 `pending`。
- 决策优先级：安全、产品和渠道硬要求 > 当前任务明确约束 > 项目持久策略 > Agent 对适用性的判断 > 仍无法判断时询问。`enabled` 是允许且适用时优先，不是强制；`disabled` 只关闭可选能力。
- 协作语义：并行策略启用后，Agent 在任务可拆、文件所有权独立且 Worktree 门禁可满足时自行使用；否则自行回退单 Agent，不重复询问。该决定替代 ADR-20260730-001 与 ADR-20260730-002 的“每个编码任务重新询问且不得继承”部分，保留隔离、guard、前台状态和同步等待安全规则。
- 验收语义：冒烟和 E2E 分开记录，只能在 Todo 批次完成后的验证里程碑消费。产品/渠道硬要求仍不可由 `disabled` 绕过；新增凭据、生产副作用或不可逆操作仍需独立授权。
- 影响范围：`docs/AGENT_POLICY.md`、初始化/实例化/并行/计划/实现/验证/E2E/发布 Skills、`AGENTS.md`、README、工程与发布文档、工作流、校验器和项目记忆。
- 风险：旧下游缺字段；“策略启用”可能被误读为“所有任务强制执行”；初始化首次写入发生在 ADR 尚未创建前。
- 验证：增加模式定义正向与缺字段、非法值、残留 `pending` 负向测试；验证裁剪后策略保留和各消费入口只在适用阶段读取。初始化引导首次写入不要求预建 ADR，后续永久策略修改必须新增 ADR。
- 调整标准：若真实项目证明某项必须按场景而非项目持久化，可在保留唯一事实源和不静默继承的前提下增加受约束的临时覆盖字段；不得恢复无条件逐任务询问。

## ADR-20260731-003：新增 `$upgrade-harness` 维护终端下游的 Harness 工程部分

- 日期：2026-07-31
- 状态：Accepted
- 关联需求：新增一个用于更新下游项目 Harness 工程部分的 Skill。
- 背景：LIM-016 已记录既有下游缺少差异检测、选择性合并和冲突处理；下游不继承 Harness `Version.md`，也没有上次应用来源和逐文件共同基线。
- 决定：新增并在初始化裁剪后永久保留 `$upgrade-harness`。Skill 默认试运行，要求用户明确提供 Harness 来源，使用 `.harness/upstream-lock.json` 保存上次应用的 Harness 版本/来源与受管文件的上游/下游基线摘要；该锁文件不是产品版本源。
- 所有权模型：文件分为 `managed`、`merge-sections`、`conditional`、`protected`、`tombstone` 五类；`managed-self` 是 `managed` 的机器子模式，用于让更新器在普通受管文件后按稳定顺序自更新。产品源码、测试、产品规格/产品状态、工作计划、ADR、变更记录、验证记录、技术债、产品版本、身份、接口选择、Agent 策略、许可证、Git 历史和未登记本地文件均受保护。
- 禁回迁模型：`Version.md`、`$instantiate-project`、`$initialize-rust-project`、模板校验器、模板方法论文档和 Harness 日期项目记忆为 `tombstone`，更新不得恢复。
- 合并模型：有基线时执行三方比较；只有既有目标仍匹配基线的 `update` 可逐文件自动应用，`add`/`manual_add`/`delete` 必须人工完成并重新计划；仅下游变化保留，双方变化/新增碰撞/本地修改后上游删除全部阻断。来源 Git 必须干净，计划绑定来源 `Version.md`/`HEAD` 与目标 Git/`dirty-state`；旧下游无基线时执行引导审计，所有重叠项默认冲突，用户逐项确认后才建立首份锁文件。
- 影响范围：新 Skill 与资源、初始化保留清单、Skills 地图、README、产品规格、产品状态、工作计划、技术债、校验器和测试。
- 理由：终端下游需要接收工程治理改进，但整体覆盖会破坏业务、身份和已确认决策；来源锁和三方差异是最小可靠闭环。
- 风险：身份渲染和混合所有权文件难以自动合并；旧下游首次采用时人工量较大；更新器自更新可能使前后规则不一致。
- 验证：以隔离测试夹具覆盖上游单改、下游单改、双方修改、上游删除、目标碰撞、`tombstone`、`protected` 和符号链接越界；更新器自身最后更新并由新版复验。真实下游在取得前向证据前保持 `Unverified`。
- 恢复或调整标准：若确定性三方模型无法保护真实下游，停止自动应用并退回只生成审计报告；不得通过放宽冲突门禁恢复进度。

## ADR-20260731-002：工作计划采用 TodoList 与验证里程碑两阶段状态机

- 日期：2026-07-31
- 状态：Accepted
- 关联需求：根据需求生成的工作计划必须拆成 TodoList 和验证里程碑；Todo 未完成时持续迭代实现和单元测试，整批完成后才进入里程碑验收。
- 背景：现有工作计划以步骤和结果为主，没有统一 Todo 状态、批次完成门禁和验收失败回流规则；开发循环仍允许最小冒烟。
- 决定：`$plan-change` 必须生成 Todo 批次和验证里程碑。Todo 具有稳定 ID、预期行为、影响边界、验证方式和 `pending`/`in_progress`/`blocked`/`done` 状态；任一非 `done` 项存在时禁止进入里程碑。
- 开发门禁：`$implement-change` 持续实现未完成 Todo，并以非空单元测试与必要的格式、代码规范检查、静态、集成/契约检查闭环；开发循环不得运行冒烟或 E2E。
- 里程碑门禁：整批 Todo 完成且开发检查通过后，才构建并验收真实里程碑产物。冒烟/E2E 只在这里按 `docs/AGENT_POLICY.md`、硬要求和适用性决定，其他流程不触发。
- 失败回流：批准范围内的缺失/偏差重开或新增 Todo 并回到实现；新产品边界返回 `$define-product`。修复后增加回归测试并重新验收完整里程碑。
- 影响范围：`$plan-change`、`$implement-change`、`$verify-delivery`、`$test-final-artifact-e2e`、构建/发布/适配器 Skills、工程规则、发布文档、工作流、校验器和项目记忆。
- 理由：把“代码完成”和“场景验收”分离，能保持开发反馈快速，同时避免半成品进入接受流程。
- 风险：Todo 粒度过小会制造清单噪声，过大会掩盖未完成逻辑；状态可能被无测试地提前改为 `done`。
- 验证：校验器要求计划结构和阶段禁令；单元测试覆盖状态门禁与失败回流文本契约；真实项目证据未建立前标记 `Unverified`。
- 调整标准：可根据真实项目合并或拆分 Todo，但必须保留批次完成门禁、非空单元测试和失败回编码状态机。

## ADR-20260731-001：只有完整可运行且符合批准场景的真实里程碑产物可被验收

- 日期：2026-07-31
- 状态：Accepted
- 关联需求：项目验收对象必须是完整、可运行、符合描述场景的里程碑产物，而非一段模拟实现；未达标时返回编码实现缺失逻辑并修复偏差。
- 背景：现行规则能区分中性脚手架与产品交付，也禁止把测试当成人工批准，但允许 `Partially verified` 停留在缺失实现或偏差仍存在的状态，且“最终产物”与“里程碑完整性”的入口条件不够明确。
- 决定：源码片段、模拟实现、桩实现、占位页面、中性脚手架、开发预览、只调用内部函数或仅证明能编译的输出均不具备里程碑验收资格。验收候选必须绑定批准场景、真实产物、源码提交、当前环境和可观察结果。
- 失败处理：若缺失或偏差属于已批准范围，Agent 不得仅报告未通过后结束；必须保存失败证据，返回编码，补齐逻辑、修复偏差、添加回归测试，再重新构建和验收。只有范围变化、破坏性操作、新外部副作用或持续无法判断才请求用户。
- 人工边界：Agent 可以确认自动门禁和场景证据，最终人工复核仍由人类签署；`Partially verified` 不是“已验收”的同义词。
- 影响范围：产品规格、工作计划、实现/验收 Skills、工程与发布规则、验证记录、变更记录和校验器。
- 理由：验收的目标是证明用户场景闭环，而不是证明存在若干代码或模拟实现。
- 风险：里程碑边界描述不清会导致无限返工；外部平台或凭据缺失可能不是编码缺陷。
- 验证：每个里程碑明确包含/不包含、真实产物身份、成功与最高风险失败场景；把编码偏差与外部 `Unverified` 前置条件分开记录。
- 恢复或调整标准：若真实项目需要探索性原型，必须明确标为“不可验收原型”并建立独立范围；不得降低正式里程碑验收资格。
