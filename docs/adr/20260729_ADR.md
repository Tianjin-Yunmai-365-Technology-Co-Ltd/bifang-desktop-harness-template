# 2026-07-29 ADR

## ADR-20260729-001：逐任务授权的前台并行 Worktree 与 Subagent 模式

- 日期：2026-07-29
- 状态：Accepted
- 关联需求：每次任务开始执行前询问用户是否启用并行 Worktree 和 Subagent；Subagent 执行过程不得作为用户不可见的后台工作。
- 背景：复杂变更可从并行拆分受益，但自动并行会增加分支、Worktree、冲突与资源管理成本；只在后台运行 Subagent 又会削弱用户对任务范围、阻塞和整合状态的判断。
- 决定：对会修改仓库或执行交付工作的任务，在实质执行前询问一次且只对当前任务生效。用户明确同意、任务至少有两个独立子任务且文件所有权可分离时，写入型 Subagent 各自在独立 Git Worktree 与 `codex/` 分支工作；纯只读子任务可共享只读上下文。主 Agent 在启动、阻塞、阶段完成、整合和验证节点发送用户可见更新，并同步等待所有必需结果后才能结束任务。纯问答、只读调查和即时安全处置不触发询问；拒绝、未答复或不可安全拆分时使用单 Agent 流程。
- 影响范围：`AGENTS.md`、README、Product Spec、Product Status、Work Plan、相关规划/实施/验证 Skills、新增协作 Skill、Harness validator、验证与 Changelog。
- 不包含：不逐行展示内部推理，不让多个写入者修改同一工作树，不自动 push、发布或删除含未整合修改的 Worktree。
- 理由：逐任务授权保留人类控制；Worktree 隔离降低并行写入冲突；明确阶段更新和同步等待在不暴露内部推理的前提下提供可审计可见性。
- 风险：Codex 宿主对状态流的展示能力可能不同；过细更新会制造噪声；Worktree 可能残留；错误拆分仍可能产生语义冲突。
- 验证：validator 检查授权、隔离、可见节点、同步等待、拒绝回退和安全清理契约；使用隔离临时 Git 仓库验证 Worktree 脚本的正向与风险失败路径；真实 Subagent 宿主交互在发布前 E2E 记录。
- 恢复或调整标准：若并行模式不能稳定降低周期或导致冲突、残留和用户认知成本上升，保留逐任务询问但默认推荐单 Agent，或在新 ADR 中收紧适用条件。

## ADR-20260729-002：开发轮次验证与发布整体验收分层

- 日期：2026-07-29
- 状态：Accepted
- 关联需求：每轮开发仅进行单元测试与验证，把整体验收适当延迟到用户准备发布前。
- 背景：每次小改动重复最终产物构建、启动冒烟、E2E、跨平台和人工整体验收，会拖慢开发反馈；但若只运行单元测试，也可能遗漏格式、编译、契约或变更相关风险。
- 决定：每轮开发执行非空单元测试与变更相关的必要验证，必要验证可包含格式、lint、静态检查、目标集成/契约测试和最小只读冒烟。最终产物、完整构建矩阵、归档与人工最终复核默认延迟到用户发起最终产物构建或发布准备时；发布准备必须基于当前源码重新运行基础完整闭环，历史结果不能替代。Computer Use E2E 等重型验收的触发、选择与阻断语义由 ADR-20260729-003 进一步收紧，不因交付复核或发布链路修改自动执行。
- 影响范围：`AGENTS.md`、Product Spec、工程规则、计划/实施/验收/发布 Skills、`docs/VERIFICATION.md`、`docs/RELEASE.md` 与 validator。
- 不包含：不允许零测试，不取消缺陷回归测试，不允许把失败结果交给下一轮，不把日常验证结论标记为发布就绪。
- 理由：把快速反馈与发布可信度分开，既减少重复成本，又保留与改动风险相称的即时证据和发布前完整门禁。
- 风险：变更相关验证选择不足可能延迟发现集成问题；长时间不做完整验收可能积累风险；发布前一次性暴露问题会增加修复压力。
- 验证：validator 检查开发门禁和发布门禁没有混用；测试覆盖成功路径、最高风险失败路径和发布触发条件；发布前运行完整 Harness 与 bundled asset 验证并记录未验证平台。
- 恢复或调整标准：若发布前集中失败频繁或修复成本上升，则按失败数据把对应集成、构建或冒烟检查前移到受影响开发轮次，而不恢复无差别全量验收。

## ADR-20260729-003：发布构建前逐项选择的手动验收与打包门禁

- 日期：2026-07-29
- 状态：Accepted
- 关联需求：让 Harness 更适合敏捷开发；Computer Use E2E 及同类重型、交互式或真实环境验收只由用户在构建/发布任务中手动启用，已启用或硬要求的验收失败时禁止继续打包。
- 背景：ADR-20260729-002 已把发布整体验收移出日常开发，但“进入交付验收或修改发布链路时自动执行适用 E2E”的描述仍可能在普通复核中触发耗时、交互式或有真实环境依赖的操作。与此同时，编译、测试、产物存在性和启动冒烟属于发布候选可信度的基础，不能一并变成可选项。
- 决定：Computer Use E2E、真实设备、真实宿主交互及同类重型验收不得由日常开发、普通交付复核或发布链路修改自动触发。只有用户发起最终产物构建或发布准备时，Agent 才在首次发布构建前列出具体项目并询问本次是否启用；选择只对当前任务有效。产品规格或发布渠道明确要求的项目直接标记为必需，不提供跳过选项。无论选择如何，当前源码的编译、非空单元测试、相关集成/契约、最终产物构建与存在性、真实产物只读启动冒烟均为不可跳过门禁。启用或必需的手动验收在最终产物构建后、任何打包、上传、产物收集、签名或发布动作前执行；失败、超时、取消或选择后未执行均阻断当前任务，不能在同一任务中通过取消选择绕过。未启用且没有硬要求时记录 `Not run`、原因和风险后可以继续。
- 影响范围：`AGENTS.md`、README、Product Spec、Product Status、Work Plan、工程规则、验证与发布文档、Rust 基线摘要、交付/E2E/构建/发布/收集与 adapter Skills、候选 workflow、Harness validator 和 Changelog。
- 不包含：不取消或软化基础发布门禁，不自动启用任何手动验收，不把用户选择解释为执行通过，不授权打包、签名、上传、tag 或发布，不在本次规则变更中运行真实 E2E 或 release build。
- 理由：把高成本、交互式和真实环境验收置于明确的人类控制下，能缩短普通开发与复核反馈；同时用不可跳过的基础闭环和“启用即成为打包门禁”保留发布可信度，避免可选测试沦为无效提示。
- 风险：用户不启用可选验收时，真实交互缺陷可能进入候选；发布渠道硬要求识别错误会造成违规发布；workflow 顺序错误可能在验收前已产生打包或签名副作用；用户可能尝试在失败后关闭选择以绕过门禁。
- 验证：语义审查确认当前入口不再把交付复核或发布链路修改等同于 E2E 授权；单元/契约测试与 validator 覆盖未启用可继续、启用通过可继续、启用失败/超时/取消/未执行阻断、硬要求不可跳过、基础门禁失败始终阻断，以及打包动作严格位于验收之后。真实 E2E、release build 和打包在本次开发任务中为 `Not run`。
- 恢复或调整标准：若人工选择导致必需风险长期漏测，优先把有证据的项目升级为产品/渠道硬要求；若询问噪声过高，收敛验收清单而不恢复自动触发。当前任务的已启用或必需项目只有成功重跑后才解除阻断；放弃当前任务不产生可复用的通过证据，新任务仍须重新询问。
