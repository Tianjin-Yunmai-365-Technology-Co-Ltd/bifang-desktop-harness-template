# 2026-07-28 ADR

## ADR-20260728-001：开源与闭源商业化路线调研报告

- 日期：2026-07-28
- 状态：Accepted
- 关联需求：项目负责人要求面向个人开发者和小型软件公司，从开源与闭源两个角度形成两份商业化 Word 报告；结合五人开发团队、大量低客单价客户、交付终端派生项目和首年验证目标，先检索竞品与相似开源项目，再统一落盘。闭源路线还需评估按目标终端裁剪 Skills/知识库以及未来私有实现库的方案。
- 背景：Harness 的主要资产是可被 Agent 读取的方法、规则、文档和一次性派生流程，纯文档难以通过技术手段阻止复制；团队又不具备自研通用 Agent 或大规模 SaaS 运维能力。因此商业化设计必须把首年验证、低人工支持和可持续壁垒分开处理，避免把“隐藏文档”误当成护城河。
- 决定：在仓库根目录生成开源路线和闭源路线两份内部商业化调研 DOCX，引用截至 2026-07-28 核对的官方文档、官方仓库、官方产品页和开发者调查。开源报告把“有限开源精简版 + 付费验证/更新/终端包”作为优先实验，不建议首年完整开放全部生产方法与派生能力。闭源报告建议采用“内部完整 Harness → 按终端生成与裁剪 → 客户最小可维护项目”的边界；只有同一能力在至少 3–5 个真实付费项目中重复、接口稳定且节省量可量化后，才抽取为闭源组件。需要隐藏实现时，优先采用版本化协议的本地 CLI/伴随进程；私有 Cargo 软件包仓库只作为访问控制和复用机制，不宣称能在客户构建时隐藏 Rust 源码。
- 影响范围：根目录两份商业化调研 DOCX、当日 ADR、产品状态、工作计划、变更记录和验证记录。报告中的价格、转化率和路线图是待验证假设，不是正式报价、销售承诺或发布计划。
- 不包含：不修改当前 Approved 产品规格，不改变现行企业专有商业许可，不把开源路线视为已批准许可变更，不实现支付、许可服务器、私有库、云服务或新的 Agent，也不授权发布或对外销售。
- 理由：两份独立报告让团队可以在相同客户、产能和首年目标下比较获客与保密取舍；以真实付款、首次成功时间、支持耗时和重复实现比例作为门槛，能防止五人团队过早投入复杂基础设施。终端裁剪能减少无关能力暴露和客户认知负担，但真正壁垒仍来自持续验证、兼容、回归和交付数据，而非文件不可见本身。
- 风险：竞品价格、功能、星标数量和产品阶段会变化；公开资料不能证明市场规模或本项目付费意愿；报告的许可证与合同建议不构成法律意见；本地闭源二进制仍可被逆向，裁剪也不能形成绝对防复制。正式销售前需要重新核价、法务复核，并以真实订单数据校准假设。
- 验证：两份 DOCX 均通过 ZIP 结构检查和文档可访问性审计，高/中等级问题为零；开源报告 9 页、闭源报告 11 页，已逐页渲染检查封面、表格、编号、超链接、页眉页脚和分页。运行 `python3 scripts/validate_harness.py` 检查项目记忆与仓库契约；执行结果写入 `docs/VERIFICATION.md`。
- 产品规格同步：`Not applicable`。本次产物是内部策略研究，不批准新的产品功能、许可模式或发布范围；当前产品规格与企业专有商业许可继续有效。README、Version、发布和业务接口同样无需修改。
- 恢复或调整标准：如首批 90 天实验无法获得至少 10 名陌生付费用户，或支持中位数超过报告门槛，应先调整定位、交付和价格，而不是抽取私有组件。任何正式开源、双重许可、SaaS、OEM 或私有组件产品化都必须新增 ADR，并同步产品规格、许可证、计划和验证门槛。
