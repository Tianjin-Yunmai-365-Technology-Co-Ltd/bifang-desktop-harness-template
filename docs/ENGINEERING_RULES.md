# 工程规则

本文档是所有下游项目在文件组织、代码注释、文档维护、测试组织、规则例外和机械检查方面的唯一详细事实来源。`AGENTS.md`、项目 Skills 和技术基线只保留任务入口、语言特定补充与本文件链接，不复制整套规则。

## 1. 适用范围与规则等级

- 本规则适用于所有由 Harness 建立或维护的下游项目。通用规则不绑定语言；语言或工具链文档可以增加不削弱本规则的具体要求。
- Harness 自身的文档、Skills 和随附的中性资产必须体现本规则。新建和本次修改的内容立即遵守；未触及的存量维护脚本采用渐进治理。
- **硬规则**用于保护架构边界、正确性、跨平台能力和交付可信度。违反时必须修复；确需例外时按第 6 节记录决策。
- **默认规则**用于保持可读性和一致性。有真实、局部且可说明的理由时可以偏离，不要求为普通组织选择增加正式决策记录。

## 2. 文件、模块与依赖边界

### 2.1 硬规则

- Core-first 是硬规则。凡不依赖某一具体接口或宿主才能成立的领域类型、业务规则、语义校验、业务默认值、应用用例与工作流编排、领域状态转换、稳定领域错误、平台无关权限、权威业务状态、迁移和持久化策略，都必须在共享 core 中实现并通过 core 自有类型的明确 API 暴露；即使当前只选择一个适配器也同样适用。
- CLI、TUI、MCP、GUI 适配器必须保持薄层，只负责运行时与依赖装配、接口语法或协议结构解析、展示和纯交互状态、调用 core，以及把 core 结果和错误映射为接口输出。薄层按职责判断，不按文件行数、分支数或协议映射代码量判断。
- 适配器不得复制、改写或另建业务规则、平台无关校验、业务权限、权威业务状态、迁移、持久化策略或稳定领域错误。适配器处理器若需要用条件、重试或状态决策编排多个 core 调用，必须把该编排提升为一个 core 用例 API。
- 输入检查必须区分接口语法/协议结构与领域语义。无法解析、缺少协议必填字段或违反宿主能力约束的调用可由适配器拒绝；值域、跨字段关系、资源状态、业务权限、幂等性、可否执行和会改变业务结果的默认值必须由 core 判定，并在所有适配器中保留同一稳定领域错误。
- 接口或宿主特有机制属于对应适配器：例如 CLI 参数、标准流和退出码，MCP schema 注解与 stdio 生命周期，TUI 焦点、选择、滚动、按键和终端恢复，以及 GUI 路由/查询/交互状态、窗口、WebView、CSP、系统托盘、通知和自动启动。托盘点击、快捷键、通知动作或界面事件触发的业务行为仍必须调用 core；这些平台机制本身不构成 core-first 例外。
- 文件系统、网络、外部进程和操作系统 API 等具体驱动集中在职责明确的适配器或基础设施模块。何时调用、允许什么、失败如何解释以及结果怎样改变领域状态属于 core；真实边界需要时可由 core 定义运行时中立的能力接口并由适配器装配实现，不得为假想未来预建抽象。
- GUI 初始化固定建立 adapter-only 基线：先实际生成正好 3 个 1024×1024 Logo 候选并由用户明确选择，选中母版同时生成平台图标和本地 `/app-identity/logo.png`；托盘只含“显示窗口/退出”，主窗口关闭只隐藏；标题动态组装；左侧菜单默认收起，顶部始终先显示选中 Logo、再紧接当前版本，两种状态均不得隐藏二者。每个功能项和赞助/设置/关于固定项都必须提供图标；折叠时显示图标并以本地化 Tooltip 补充名称，展开时显示图标与名称，两种状态均保留可访问名称。产品功能从顶部向下增长，底部固定为赞助、设置、关于；固定 `/settings`、`/about`、`/sponsor`。主应用窗口初始为 1440×900 逻辑像素、最小 960×640、居中并防止溢出，展开 248px 侧栏时仍能横向显示三张赞助档位卡；它与 660×400 的 DMG 安装卷窗口独立。Mantine 根通过唯一主题入口同时提供亮色/暗色的页面背景、surface、主/次文字、边框与强调色，默认跟随系统；设置页提供浅色、深色、跟随系统三态选择并持久化。设置页同时提供中英文和默认关闭的统计同意；手动检查更新位于关于页，未配置远端能力时显示 `NotConfigured`/禁用并零出站。关于页还展示作者、联系方式和免责声明，赞助页按运行时有效主题选择背景叠层、surface 与对比色并打包 sponsor 媒体。真实更新启用时使用官方 Tauri updater 签名制品，强更只由 core 对 adapter 已认证的最低支持版本作 SemVer 判定；统计只在明确同意后由 Rust adapter 以 HTTPS JSON POST 发送固定最小字段，撤回即取消与清队列。Logo、窗口、托盘、路由、主题/语言偏好、平台元数据和传输属于 GUI adapter；跨接口资格、默认值和状态转换属于 core。桌面 bundle 不能保密，服务端 secret、共享口令和发布私钥不得进入源码、文档、样例、日志、配置或前端 bundle；全部远程任务必须有 owner、取消、超时、上限和关闭回收。
- `$desktop-prepare-gui-support-surfaces` 维护产品家族共享的固定本地页面/媒体依赖资产；固定赞助档位/价格、作者、品牌联系人、免责声明、支付二维码、更新 banner 与小图是经项目负责人批准的封闭例外。每个媒体文件必须有可审计清单、尺寸、摘要、用途、来源与许可责任；支付二维码必须标记为敏感支付材料，随默认赞助页进入 GUI bundle，但携带或展示它不授权订单、权益、账户或自动支付逻辑。updater banner 只有选择更新视觉时才进入 bundle。图片提供语义化替代文本或显式装饰声明。视频必须本地打包、提供 controls、字幕轨和文字稿、禁止 autoplay 与远程追踪。来源下游产品名称/标识、固定 endpoint、秘密与遥测实例不得进入品牌资产包。
- GUI 前端固定直接依赖 `@tabler/icons-react`，并以命名组件提供菜单、操作、状态、空态和图表周边图标；存在适用 Tabler 图标时不得引入其他图标库、手写 SVG、字符或 emoji。图表绘制能力仍按真实数据可视化需求单独选择。默认收起侧栏必须显式把 Logo 与每个当前渲染图标水平居中且无裁切。
- 含 GUI 的一次性初始化必须在相关非空单元测试通过后、裁剪初始化能力和创建唯一基线提交前运行 `$desktop-test-gui-initialization-e2e`：构建并启动本次真实本机调试二进制，以 Computer Use 验证可见主窗口、收起侧栏居中和全部渲染菜单页面可达。该门禁独立于 `milestone_e2e`，不写 release/Verification；失败、超时、取消或无法执行都阻断初始化。
- 依赖方向必须清晰：每个适配器直接依赖 core；core 不得直接或通过 workspace 中间 crate 反向到达 CLI、TUI、MCP、GUI、终端 I/O、进程状态或接口框架；适配器彼此不得直接或通过 workspace 中间 crate 依赖、启动或解析输出。
- 程序入口和接口处理器只负责建立运行环境、装配依赖、委托调用和映射终止结果，不得承载业务规则。
- 只有独立发布、独立生命周期、独立权限或由工具链强制要求的依赖边界才能新增 crate/包。新增时记录它为什么不能只是现有模块。
- 直接依赖和受管工具的清单必须表达经过验证的最低兼容稳定版本范围。Rust registry 依赖使用包含完整三段下界的 Cargo 兼容要求；前端 `dependencies`/`devDependencies` 使用包含完整三段下界的 caret 或官方支持范围；Node.js、包管理器及 cargo-xwin 等带 SemVer 的受管工具使用显式兼容范围。普通依赖不得使用精确 `=`、前端裸版本、`latest`、tag、通配符或无下界范围；例外必须按第 6 节记录。
- 锁文件与兼容要求职责分离：根 `Cargo.lock` 和 `pnpm-lock.yaml` 固定当前实际解析结果以保证日常可复现，但不是最低兼容版本的事实来源。每个新增或提高的直接下界都必须在项目声明的最低 Rust/Node.js/pnpm 工具链中完成最低直接版本解析，并运行受影响的非空测试；正常锁定解析可以选择范围内较新的稳定版本。
- 应用发布版本、协议/模式版本、Rust edition、平台目标三元组、资产摘要和按安全要求钉住的 CI action commit 不属于依赖兼容范围，不得为了形式统一改写成依赖版本范围。
- 自动生成代码、内嵌的第三方代码和人工维护代码必须明确隔离。不得直接修改生成物或内嵌的第三方内容。

### 2.2 默认规则

- 按职责、变化原因和领域概念拆分，不按类型数量、文件对称性或假想未来机械拆分。
- 一个文件围绕一个主要职责组织。总是一起变化且紧密协作的类型和函数优先放在一起。
- 出现独立领域概念、不同变化原因、平台边界或已经难以一次独立审阅时，应拆分文件或模块。
- 人工维护文本超过 500 个物理行时，必须显式复核文件中的业务是否高内聚、是否围绕单一职责，以及各部分职责是否相近。三项均成立时可以保留；任一项不成立时必须按真实职责重构拆分。
- Rust 模块需要拆分为多个文件时，使用 `<module>/mod.rs` 作为目录入口，并把职责相近的子模块放入该目录；不得同时保留 `<module>.rs` 与同名目录，也不得为规避行数创建空壳转发层。
- 不为每个类型或函数单独创建文件，不预建没有真实消费者的多层目录或扩展点。
- 禁止以 `utils`、`common`、`helpers`、`misc` 等兜底名称隐藏职责；共享代码必须使用真实领域或能力名称。
- 避免不能表达边界的 `manager`、`processor`、`handler` 等泛化名称。只有名称确实对应领域角色时才使用。
- 单元测试靠近被测单元；跨模块、CLI 契约和端到端测试放入独立测试目录。
- 只有转发作用且没有独立约束价值的模块应删除或合并。

### 2.3 单文件 500 行复核与 2000 行硬上限

- 所有由人类或 Agent 维护的文本文件都适用同一两级规模治理：500 行及以内不因行数触发专项复核；501 至 2000 行必须执行第 2.2 节的高内聚、职责单一和职责相近性复核；2000 行通过，2001 行失败并强制拆分。源码、测试、脚本、文档、配置、Skill、参考、模板和人工维护夹具使用同一阈值。
- 行数按与 Python `splitlines()` 等价的物理行计数，不扣除空行、注释或声明；不得通过压缩可读性、合并无关语句或移除必要注释规避门禁。
- 501 至 2000 行不是自动通过区间。复核必须基于真实业务边界；只有内容高内聚、围绕单一职责且各部分职责相近时才能保留，否则必须按职责拆分并修正引用后才能完成任务。
- 任一人工维护文本超过 2000 行时必须拆分；计划说明、审查结论、警告或 ADR 都不能把硬超限改判为通过。
- 工具生成且禁止手工编辑的锁文件/生成物，以及原样内嵌且明确隔离的第三方文件，不属于人工维护文件。这是封闭的范围定义，不是任意路径豁免；生成器、模板、补丁和维护说明仍受两级规模治理。
- 文件规模治理与职责判断同时成立：文件未超过 500 行不证明职责合理，adapter 未超限也不证明其符合 core-first；语义边界仍按本节其余规则审查。

## 3. 中文代码注释

### 3.1 必需覆盖

- 所有人工维护的数据结构、接口、函数和方法都必须有符合业务语义的中文注释，不只覆盖公共 API。
- 数据结构注释说明业务角色、关键状态和必须维持的不变量；语义、单位或约束不直观的字段单独说明。
- 接口或 trait 注释说明职责边界、调用约定、输入输出、错误和副作用。
- 函数与方法注释至少说明其业务目的、主要处理逻辑或关键思路、重要前置条件与边界情况，以及返回结果、错误和副作用。
- 简单取值方法、构造器和薄转发函数也需要中文注释，但可以只用一句准确说明，不得为了满足格式编造复杂逻辑。
- 测试函数注释说明测试场景、关键条件、执行思路和预期结果。

### 3.2 内容质量

- 注释解释业务含义、设计原因、关键不变量和约束，不逐行翻译代码。
- 能通过更清晰的命名或结构表达的内容，先改进代码，再保留仍然必要的业务说明。
- 修改代码时同步更新相关注释。与实现冲突的注释按缺陷处理。
- 复杂算法说明不变量、阶段和取舍，不记录可直接从控制流读出的步骤。
- 非直观兼容处理、外部限制或规避方案必须说明来源、适用条件和删除条件，并链接对应决策、上游问题或官方资料。
- `unsafe` 代码块必须紧邻安全性说明，明确调用者保证、关键不变量及其成立原因。
- 禁止保留被注释掉的旧代码；历史交给版本控制。
- 不使用署名、时间线式修改记录或“由 AI 生成”等元信息注释。
- 中文术语在项目内保持一致；代码标识符继续使用英文。

### 3.3 临时标记与有限豁免

- `TODO`、`FIXME`、`HACK` 不得裸写，必须包含具体原因和完成或删除条件。当前任务不能解决时同步登记 `docs/TECH_DEBT.md`。
- 闭包和极短内联回调可以由所属函数的注释统一说明。
- 自动生成代码和内嵌的第三方代码豁免；宏展开结果由宏定义处统一说明。
- 纯声明型测试数据、静态常量集合和测试夹具可以通过所属模块或数据集说明统一覆盖。
- 豁免只消除逐项注释要求，不允许隐藏安全约束、数据来源或容易误用的业务语义。

### 3.4 机械存在性门禁

- Rust 下游必须保留 `.agents/skills/desktop-implement-change/scripts/check_rust_chinese_comments.py`，但只在本次变化需要、用户明确请求治理检查或发布/渠道硬要求时运行；日常开发和普通构建不为它增加独立步骤。它从 Cargo package 或 virtual workspace 根解析成员，扫描每个 package 的 `build.rs`、`src/**/*.rs` 和 `tests/**/*.rs`，并对人工维护的 `struct`、`enum`、`union`、type alias、trait、具名函数、关联函数、方法和测试函数检查声明自身是否具有紧邻、包含至少一个汉字的 outer doc comment。attribute 可以位于文档注释与声明之间。
- Rust 门禁不要求逐字段、局部变量、闭包或宏展开产物；非直观字段仍按第 3.1 节语义复核。模块注释、父项注释、普通 `//`、纯英文文档注释或字符串中的中文不能替代声明自身的证据。
- 选择 GUI 的下游必须在 GUI 前端保留 TypeScript Compiler AST 中文注释门禁，并同时接入 `pnpm lint` 与项目 validator。机械范围只包括 interface、type alias、enum、class、具名函数、方法/访问器/构造器、直接或后置命名/默认导出的箭头函数组件与 hook，以及测试文件或显式 `vitest` 导入中的 `test`/`it` 测试场景；显而易见的字段、局部变量、循环绑定和普通匿名/极短内联回调不逐项检查，继续由所属结构或函数注释覆盖。
- TypeScript 门禁只精确排除已声明的生成物（例如根相对的 `src/routeTree.gen.ts`）和依赖/产物目录，不得因任意路径片段名为 `build` 等通用词而跳过人工源码。Rust 与 TypeScript 门禁都必须对无有效扫描对象、语法残缺、非法 UTF-8、NUL、源码符号链接、坏 JSON 或运行超时失败关闭，并报告根相对文件、行、列、声明类别和名称。
- “包含至少一个汉字”只证明注释存在且归属正确，不证明内容有业务意义；语义质量仍按第 3.2 节由人工或 Agent 复核。门禁不得自动生成或批量补入“保存变量供当前逻辑使用”“执行处理逻辑”等套话。
- 非 GUI 下游不得因为 TypeScript 门禁要求安装 Node.js 或 pnpm；GUI 下游以 `$desktop-add-gui-adapter` 的前端基线和门禁参考实现为唯一接线来源。

## 4. 文档规则

### 4.1 单一事实来源

- 每项事实只能有一个权威来源。其他文档可以摘要并链接，但不得复制一份会独立演化的规则。
- 文档与代码、配置或测试冲突时，必须调查真实行为并在同一任务中修正，不能默认任一方正确。
- 文档中的命令、路径、配置项、版本和能力必须来自真实仓库，不得虚构或把计划中的能力写成已实现。
- 未确认信息明确标为“待确定”，未运行检查标为“未执行”，未实际验证的平台或行为标为 `Unverified`。
- 产品目标、边界、约束或成功标准变化时更新日期最新的 Product Spec；长期重要、难以逆转的决定和硬规则例外写入当日 ADR。范围清楚的日常实现不为每项需求创建 ADR。
- Product Status 只在重要阻断、跨会话交接、发布/完整验收或用户要求时更新；Work Plan 只在用户明确要求、跨会话交接或发布/高风险协调确有必要时维护；Verification 只保存发布、完整验收、人工复核或需要长期审计的证据。
- 普通缺陷修复、不改变可观察行为的纯重构、格式整理、测试补强和内部清理本身不触发 Product Spec、ADR、Product Status、Changelog 或 Verification；结果只在最终回复和测试/CI 中报告，不写“不适用”占位。已有 TECH_DEBT 条目在问题消除后必须恢复真实状态，但不新增修复流水账。
- 构建请求、执行、成功、失败、重试、全量单元测试结果、产物路径/摘要/签名状态和本次 E2E 选择本身不触发 Product Spec、ADR、Changelog、Product Status、Work Plan 或 Verification。构建事实只写入当前 `release/` manifest、其声明的相邻制品证据和最终回复，不得复制到项目记忆；E2E、完整验收、发布、人工复核或长期审计被独立触发时，才由对应 Skill 按自身事实源留证。
- 同一维护任务若另外改变产品目标/边界/约束/成功标准、引入长期决定或硬规则例外、形成重要阻断/交接、进入发布/人工复核/长期审计，或触发安全/渠道硬要求，只按该独立事件更新对应记忆。任务被称为“修复”或“重构”不能绕过门禁。
- 除上述维护排除外，用户或维护者可感知且符合 Changelog 资格的真实行为/流程变化写入当日 Changelog。修改代码或规则时仍须同步受影响的权威设计文档和测试；同步事实不等于创建项目记忆。
- 修改工程规则时，同步检查 `AGENTS.md`、相关 Skill、本文件和适用的机械检查。
- 删除或替换规则时清理失效入口、链接和摘要，避免旧规则继续进入 Agent 上下文。

### 4.3 编写、拆分与归档

- 标题和首段先给结论，再补充原因、边界和证据。
- 规则必须说明做什么、何时适用、如何验证和允许什么例外，避免无法判定的“适当”“尽量”或“一般来说”。
- 示例必须标明是规范示例、占位示例还是真实验证结果，不得混淆。
- 内部链接使用相对路径；外部技术结论优先链接官方来源，并记录核对日期。
- 日期统一使用 `YYYY-MM-DD`；状态使用仓库规定的固定词汇。
- 文档不保存被删除内容的注释版本；历史交给版本控制、决策记录、验证记录或变更记录。
- 所有文档同样受 500 行复核与 2000 行硬上限；超过 500 行时优先识别独立主题，职责不再单一或相近时拆为有明确职责的文档，并由原入口保留目录和链接。
- `README.md`、`AGENTS.md`、方法论和项目记忆没有长文档例外；拆分必须保持每项事实的唯一来源、稳定入口、历史失败证据与人工复核事实。
- Product Spec、Product Status 和 Work Plan 只有触发条件满足时才写入；同一天只更新各自唯一日期文件，不得为同一天创建第二份。
- 需要在新自然日写入上述记忆时，先读取前一份，将仍有效事实、未完成事项和当日变化综合重写为完整当前快照，不得只写增量。
- 产品状态日期文件始终重写为当日完整当前状态，不累积流水账。
- 工作计划日期文件只保存当日完整当前计划。结果进入状态、验证、决策和变更记录；旧日期文件随即删除，历史由 Git 版本控制承担，不另建 `docs/archive/work-plans/` 副本。
- `docs/verification/` 与 `docs/verification/human_review.md` 记录的已发布版本、真实人工复核和真实验证执行证据保留历史，不得改写为通过或删除失败事实；ADR、Changelog、Work Plan、Product Status、Product Spec 五类按日记忆只保留日期最新的文件，历史由 Git 版本控制承担（见 ADR-20260805-004）。
- 同一未发布日期文件内，已被后续决定完全替代且会污染当前检索的规范描述可以合并为最新有效表述；合并必须新增 ADR 记录范围、理由、风险和恢复依据，并保留仍有效的决定编号、人工复核事实与失败证据。
- 日期文件名使用紧凑日期 `YYYYMMDD`，正文日期仍使用 `YYYY-MM-DD`。同一天不得创建第二个产品规格、产品状态、工作计划、ADR 或变更记录文件。
- 涉及产品边界、长期规则、硬规则例外或完整候选复核时先读 ADR 索引与最新日期 ADR；日常开发只在受影响区域存在相关决定时读取。只有最新条目显式引用仍有效的旧日期事实时才继续追溯。

## 5. 测试组织

### 5.1 覆盖与边界

- 每个代码行为变更必须由本次开发需要的相关非空单元/回归测试覆盖核心成功路径和最高风险失败路径；纯文档、元数据、格式或不可合理单测的机械变更只做解析或差异完整性所必需的最小替代检查。
- 修复缺陷时必须增加能够复现该缺陷的回归测试；无法测试时记录原因、风险和替代验证。
- 核心业务规则优先使用单元测试；跨模块契约、CLI 和真实边界使用集成或黑盒测试。
- 新增或修改业务行为时，必须先由 core 测试覆盖成功路径和最高风险领域失败，再由适配器测试覆盖输入/协议/视图映射、接口错误和生命周期。仅有适配器测试不能证明业务行为符合 core-first。
- GUI 远程能力至少测试未配置/未同意/撤回时零出站，以及方法、允许地址、字段、重定向、响应大小、超时、取消和秘密脱敏中的最高风险失败。更新另测认证最低支持版本的 SemVer 强更边界、target/channel 与制品签名；统计另测只用 POST 固定字段、无稳定标识符、有界内存队列与撤回清空。后台任务必须有 owner、取消路径与关闭回收，不能用 detached task 或无限重试冒充 fail-open。
- 每个新增公开操作必须能够追溯“适配器操作 → core 用例 API → core 测试”。只修改布局、协议映射或平台机制而不改 core 时，计划或完成输出必须说明其接口/宿主专属性；多适配器暴露同一行为时必须复用同一 core API 和稳定领域错误。
- CLI 的真实二进制契约测试在显式构建、完整验收或用户明确要求时运行，验证标准输出、标准错误、JSON、退出码和非交互行为；日常开发仍只运行本次必要单元/回归测试。
- 测试验证可观察行为，不与无关实现细节耦合；内部重构不应无故导致大量测试重写。

### 5.2 隔离与可维护性

- 测试默认确定、隔离且可重复，不依赖真实网络、当前时间、随机顺序、用户主目录或机器已有状态。
- 需要文件系统时使用独立临时目录；测试不得读写真实用户数据或共享持久状态。
- 被忽略、跳过或依赖特定环境的测试必须说明原因、启用条件和影响，并在验证报告中列为未执行。
- 测试名称使用英文 `snake_case` 表达场景、条件和预期结果；测试函数按第 3 节添加中文注释。
- 小型测试夹具靠近测试；大型测试夹具放入 `tests/fixtures/`，保持只读并注明来源和用途。
- 测试辅助代码只在重复且语义稳定时抽取，禁止建立不透明的通用测试框架。
- 测试文件、测试支持和人工维护夹具同样适用 500 行复核与 2000 行硬上限；超过 500 行且场景或职责不再高内聚时应按场景或领域拆分，不能以数据密集为由跳过语义复核。

### 5.3 开发、构建与完整验收

- 日常开发统一直接实施，只运行本次变更需要的相关非空单元/回归测试。不得仅因多步骤、多模块、中等风险、可并行或 Agent 偏好自动增加 Work Plan、全仓测试、格式化、代码规范、静态、集成/契约、构建、冒烟、E2E、Verification 或人工复核。
- 产品范围、长期决定、合格 Changelog、重要阻断/交接、发布/审计和用户明确要求仍分别触发对应记录或专用流程。安全/隐私、数据迁移、破坏性操作、凭据/生产/付费副作用、对外兼容契约、渠道硬要求、签名与发布仍保留解决当前风险必需的授权和门禁。
- 显式构建在任何测试或编译前解析当前构建的 E2E 选择：当前请求已明确 `enabled`/`disabled` 时直接复用，否则询问一次；持久 `milestone_e2e` 仅是建议默认值。该选择只对当前构建有效。
- 构建必须运行项目全部非空单元测试。Rust 使用 workspace 全成员、全 targets、全 features 的锁定测试；GUI 同时运行完整 Rust workspace 和前端单元测试套件。测试失败或零测试阻断构建。
- GUI 产品启用 updater 时，Tauri 构建必须生成与当前 platform/channel/target/arch 一致的官方更新 archive 和 `.sig`，使用应用配置的公开公钥实际验证，并在 manifest 记录相对路径、大小、SHA-256 和验证结论。安装包允许 unsigned 不代表 updater 可不签名；发布私钥与密码只能来自批准的安全运行时，绝不能进入源码、配置、日志、manifest 或制品。
- 构建记录严格遵守第 4.1 节的边界：manifest 和最终回复是普通构建的记录出口，不为构建过程或结果创建、更新任何项目记忆。
- 发布候选 E2E 不混入单元测试、编译、签名或打包命令。选择启用或产品/渠道硬要求时，只在完整最终候选存在后运行；选择禁用时记录 `Not run` 和剩余风险。GUI 初始化专用的 debug/no-bundle E2E 是唯一前候选例外，只能证明脚手架在当前宿主可构建启动、侧栏居中和菜单可达，不能形成候选验收结论。
- 完整候选必须绑定批准场景、源码提交、运行环境和可观察结果；模拟实现、测试替身、占位页面、中性脚手架、开发预览、源码片段或只调用内部函数的结果不具备验收资格。验收失败保存证据并返回开发循环；只有存在用户要求的持久计划时才重开 Todo。
- 构建候选可以标记 `milestoneAcceptance: pending`，但不是 `ready` 或发布物。若验收后的签名、公证或打包改变产物字节、启动器、依赖或运行行为，结果是新候选，必须重新验收。

## 6. 规则例外

- 硬规则例外必须记录到当日 `docs/adr/YYYYMMDD_ADR.md`，包含被偏离的规则、理由、风险、适用范围、替代验证和恢复条件。
- 人工维护文本超过 2000 行的硬上限不接受 ADR 例外；501 至 2000 行文件是否保留由第 2.2 节的高内聚、职责单一和职责相近性复核决定，不属于规则例外。被机械识别为工具生成或原样内嵌第三方的文件按第 2.3 节范围定义处理，不得把普通维护文件伪装成生成物。
- 默认规则允许在计划或复核记录中说明局部理由，不要求正式决策记录。
- 例外必须尽可能小，不得从单个文件或模块自动扩张为整个项目。
- 临时例外必须有删除条件；没有明确恢复路径的例外按长期架构决定处理。
- 人工批准只授权采用例外，不会把失败或未执行的验证改判为通过。

## 7. 机械检查边界

- 可确定检查的规则可以自动化，但自动化存在不代表日常开发或普通构建必须逐项运行。显式构建固定执行全量非空单元测试和实际构建；格式、lint、静态、文档链接或治理扫描只在本次变化需要、用户明确要求或发布/渠道硬要求时运行。
- Rust core/adapter 的确定依赖事实应自动检查：适配器必须直接依赖 core，core 不得直接或通过 workspace 依赖路径到达适配器或接口框架，适配器不得彼此直接或间接依赖。检查必须覆盖重命名依赖、开发/构建依赖、目标特定依赖和 workspace 可达闭包，且不得把不含接口依赖的合法基础设施 crate 误判为适配器。
- `TODO`、`FIXME`、`HACK` 格式可以由脚本报告；统一检查器必须列出超过 500 行的语义复核候选，并对超过 2000 行的人工维护文本返回失败、具体路径和实际行数。
- 公共 API 文档缺失可以由语言工具链判定失败。
- 中文声明注释的存在性和归属可以按第 3.4 节机械检查；注释是否有业务意义、模块职责是否合理、函数思路是否充分，必须由人工或 Agent 语义审查，不使用字符数、注释比例或关键词数量伪装成质量检查。
- 业务逻辑是否真正位于 core 同样必须由人工或 Agent 沿真实执行路径语义审查；不得用 adapter 行数、`if`/`match` 数量、文件名或关键词扫描伪装成完整证明。
- 自动检查失败必须返回非零状态并给出具体位置，不得只打印警告后宣称通过。
- 新规则只有在能够稳定判断、重复违规且人工容易遗漏时才升级为自动门禁。
- Harness 校验器只检查模板和随附的资产；真实下游代码仍由其工具链和交付流程验证。
