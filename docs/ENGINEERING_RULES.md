# 工程规则

本文档是所有下游项目在文件组织、代码注释、文档维护、测试组织、规则例外和机械检查方面的唯一详细事实来源。`AGENTS.md`、项目 Skills 和技术基线只保留任务入口、语言特定补充与本文件链接，不复制整套规则。

## 1. 适用范围与规则等级

- 本规则适用于所有由 Harness 建立或维护的下游项目。通用规则不绑定语言；语言或工具链文档可以增加不削弱本规则的具体要求。
- Harness 自身的文档、Skills 和 bundled 中性资产必须体现本规则。新建和本次修改的内容立即遵守；未触及的存量维护脚本采用渐进治理。
- **硬规则**用于保护架构边界、正确性、跨平台能力和交付可信度。违反时必须修复；确需例外时按第 6 节记录决策。
- **默认规则**用于保持可读性和一致性。有真实、局部且可说明的理由时可以偏离，不要求为普通组织选择增加正式决策记录。

## 2. 文件、模块与依赖边界

### 2.1 硬规则

- 依赖方向必须清晰。业务核心不得反向依赖 CLI、GUI、MCP、终端 I/O、进程状态或平台适配层。
- 平台相关行为、文件系统、网络和外部进程等边界能力必须集中在职责明确的 adapter 或 infrastructure 模块，不得散落到业务逻辑。
- 程序入口只负责建立运行环境、装配依赖、委托调用和返回退出状态，不得承载业务规则。
- 只有独立发布、独立生命周期、独立权限或工具链必须强制的依赖边界才能新增 crate/package。新增时记录它为什么不能只是现有模块。
- 自动生成代码、第三方 vendored 代码和人工维护代码必须明确隔离。不得直接修改生成物或第三方 vendored 内容。

### 2.2 默认规则

- 按职责、变化原因和领域概念拆分，不按类型数量、文件对称性或假想未来机械拆分。
- 一个文件围绕一个主要职责组织。总是一起变化且紧密协作的类型和函数优先放在一起。
- 出现独立领域概念、不同变化原因、平台边界或已经难以一次独立审阅时，应拆分文件或模块。
- 不为每个类型或函数单独创建文件，不预建没有真实消费者的多层目录或扩展点。
- 禁止以 `utils`、`common`、`helpers`、`misc` 等兜底名称隐藏职责；共享代码必须使用真实领域或能力名称。
- 避免不能表达边界的 `manager`、`processor`、`handler` 等泛化名称。只有名称确实对应领域角色时才使用。
- 单元测试靠近被测单元；跨模块、CLI 契约和端到端测试放入独立测试目录。
- 只有转发作用且没有独立约束价值的模块应删除或合并。

### 2.3 软审查阈值

- 人工维护的源文件超过约 400 行有效代码时，必须主动检查是否包含可分离职责。
- 人工维护的源文件超过约 800 行有效代码时，原则上应拆分；保留单文件需要在计划或复核记录中说明理由。
- 行数不是单独的失败条件。生成文件、声明密集型数据和测试 fixture 不适用上述数字。

## 3. 中文代码注释

### 3.1 必需覆盖

- 所有人工维护的数据结构、接口、函数和方法都必须有符合业务语义的中文注释，不只覆盖公共 API。
- 数据结构注释说明业务角色、关键状态和必须维持的不变量；语义、单位或约束不直观的字段单独说明。
- 接口或 trait 注释说明职责边界、调用约定、输入输出、错误和副作用。
- 函数与方法注释至少说明其业务目的、主要处理逻辑或关键思路、重要前置条件与边界情况，以及返回结果、错误和副作用。
- 简单 getter、构造器和薄转发函数也需要中文注释，但可以只用一句准确说明，不得为了满足格式编造复杂逻辑。
- 测试函数注释说明测试场景、关键条件、执行思路和预期结果。

### 3.2 内容质量

- 注释解释业务含义、设计原因、关键不变量和约束，不逐行翻译代码。
- 能通过更清晰的命名或结构表达的内容，先改进代码，再保留仍然必要的业务说明。
- 修改代码时同步更新相关注释。与实现冲突的注释按缺陷处理。
- 复杂算法说明不变量、阶段和取舍，不记录可直接从控制流读出的步骤。
- 非直观兼容处理、外部限制或 workaround 必须说明来源、适用条件和删除条件，并链接对应决策、上游问题或官方资料。
- `unsafe` 代码块必须紧邻安全性说明，明确调用者保证、关键不变量及其成立原因。
- 禁止保留被注释掉的旧代码；历史交给版本控制。
- 不使用署名、时间线式修改记录或“由 AI 生成”等元信息注释。
- 中文术语在项目内保持一致；代码标识符继续使用英文。

### 3.3 临时标记与有限豁免

- `TODO`、`FIXME`、`HACK` 不得裸写，必须包含具体原因和完成或删除条件。当前任务不能解决时同步登记 `docs/TECH_DEBT.md`。
- 闭包和极短内联回调可以由所属函数的注释统一说明。
- 自动生成代码和第三方 vendored 代码豁免；宏展开结果由宏定义处统一说明。
- 纯声明型测试数据、静态常量集合和 fixture 可以通过所属模块或数据集说明统一覆盖。
- 豁免只消除逐项注释要求，不允许隐藏安全约束、数据来源或容易误用的业务语义。

## 4. 文档规则

### 4.1 单一事实来源

- 每项事实只能有一个权威来源。其他文档可以摘要并链接，但不得复制一份会独立演化的规则。
- 文档与代码、配置或测试冲突时，必须调查真实行为并在同一任务中修正，不能默认任一方正确。
- 文档中的命令、路径、配置项、版本和能力必须来自真实仓库，不得虚构或把计划中的能力写成已实现。
- 未确认信息明确标为“待确定”，未运行检查标为“未执行”，未实际验证的平台或行为标为 `Unverified`。
- 需求确认时同步检查日期最新的 Product Spec、Product Status、Work Plan 以及相关架构/接口/工程设计，并在当日 `docs/adr/YYYYMMDD_ADR.md` 写入独立条目；同一天持续更新同一文件。
- 修改代码、用户可见行为或维护流程时，同步检查相关设计文档、测试、验证记录和当日 `docs/changelog/YYYYMMDD_CHANGELOG.md`。无需更新时必须在计划、ADR 或验证记录中说明不适用理由。
- 修改工程规则时，同步检查 `AGENTS.md`、相关 Skill、本文件和适用的机械检查。
- 删除或替换规则时清理失效入口、链接和摘要，避免旧规则继续进入 Agent 上下文。

### 4.2 固定职责

| 文件 | 唯一职责 |
|---|---|
| `README.md` | 用户入口、用途、真实使用方式和维护状态 |

| `docs/product_spec/YYYYMMDD_product_spec.md` | 当日完整产品目标、范围、约束和成功标准；最新日期文件是当前规格 |
| `docs/AGENT_POLICY.md` | 下游 Agent 能力开关及其持久执行语义 |
| `docs/ENGINEERING_RULES.md` | 文件、注释、文档、测试、例外和机械检查详细规则 |
| `docs/CLI_CONTRACT.md` | 下游 CLI 的统一机器接口契约 |
| `docs/RUST_CLI_TEMPLATE.md` | 下游 Rust shared core 与可选 adapter 初始化基线 |
| `docs/HARNESS_ENGINEERING.md` | 本模板的完整方法论依据 |
| `docs/project_status/README.md` | Product Status 日期规则和索引 |
| `docs/project_status/YYYYMMDD_product_status.md` | 当日完整阶段、已完成、待确认和下一步；最新日期文件是当前状态 |
| `docs/work_plan/README.md` | Work Plan 日期规则和索引 |
| `docs/work_plan/YYYYMMDD_work_plan.md` | 当日完整当前批准变更实施步骤；最新日期文件是当前计划 |
| `docs/adr/README.md` | ADR 规则与日期文件索引 |
| `docs/adr/YYYYMMDD_ADR.md` | 当日已确认需求、重要取舍和规则例外的唯一正文 |
| `docs/VERIFICATION.md` | 真实命令、结果、环境、遗漏项和人工复核 |
| `docs/TECH_DEBT.md` | 已知但不在当前任务解决的问题、影响和复核条件 |
| `docs/RELEASE.md` | Semantic Versioning、版本同步和发布要求；不重复保存 Harness 当前版本事实 |
| `docs/changelog/README.md` | Changelog 规则与日期文件索引 |
| `docs/changelog/YYYYMMDD_CHANGELOG.md` | 当日用户和维护者可感知变化的唯一正文 |

### 4.3 编写、拆分与归档

- 标题和首段先给结论，再补充原因、边界和证据。
- 规则必须说明做什么、何时适用、如何验证和允许什么例外，避免无法判定的“适当”“尽量”或“一般来说”。
- 示例必须标明是规范示例、占位示例还是真实验证结果，不得混淆。
- 内部链接使用相对路径；外部技术结论优先链接官方来源，并记录核对日期。
- 日期统一使用 `YYYY-MM-DD`；状态使用仓库规定的固定词汇。
- 文档不保存被删除内容的注释版本；历史交给版本控制、决策记录、验证记录或变更记录。
- `README.md` 和 `AGENTS.md` 超过约 200 行时检查是否应下沉细节；超过约 300 行原则上必须拆分。
- 普通规则或参考文档超过约 500 行时检查章节职责；超过约 800 行原则上按主题拆分并保留目录页。
- `docs/HARNESS_ENGINEERING.md` 是完整方法论参考，可作为长文档例外，但必须保持稳定目录和可定位章节。
- Product Spec、Product Status 和 Work Plan 同一天只更新各自唯一日期文件；不得为同一天创建第二份。
- 三类记忆在新自然日首次写入时必须读取前一份，将仍有效事实、未完成事项和当日变化综合重写为完整当前快照，不得只写增量。
- Product Status 日期文件始终重写为当日完整当前状态，不累积流水账。
- Work Plan 日期文件只保存当日完整当前计划。结果进入状态、验证、决策和变更记录；旧日期文件已提供历史边界，不另建 `docs/archive/work-plans/` 副本。
- 已发布版本、真实人工复核和真实验证执行证据保留历史，不得改写为通过或删除失败事实。
- 同一未发布日期文件内，已被后续决定完全替代且会污染当前检索的规范描述可以合并为最新有效表述；合并必须新增 ADR 记录范围、理由、风险和恢复依据，并保留仍有效的决定编号、人工复核事实与失败证据。
- 日期文件名使用紧凑日期 `YYYYMMDD`，正文日期仍使用 `YYYY-MM-DD`。同一天不得创建第二个 Product Spec、Product Status、Work Plan、ADR 或 Changelog 文件。
- 开发、规划和复核先读取 ADR 索引与最新日期 ADR；日期文件应直接给出当前有效决定，只有条目显式引用仍有效的旧日期事实时才继续追溯。

## 5. 测试组织

### 5.1 覆盖与边界

- 每个进入实现阶段的项目必须有非空测试套件，至少覆盖核心成功路径和最高风险失败路径。
- 修复缺陷时必须增加能够复现该缺陷的回归测试；无法测试时记录原因、风险和替代验证。
- core 业务规则优先使用单元测试；跨模块契约、CLI 和真实边界使用集成或黑盒测试。
- CLI 测试必须执行真实二进制并验证 stdout、stderr、JSON、退出码和非交互行为，不能只调用内部函数。
- 测试验证可观察行为，不与无关实现细节耦合；内部重构不应无故导致大量测试重写。

### 5.2 隔离与可维护性

- 测试默认确定、隔离且可重复，不依赖真实网络、当前时间、随机顺序、用户主目录或机器已有状态。
- 需要文件系统时使用独立临时目录；测试不得读写真实用户数据或共享持久状态。
- 被忽略、跳过或依赖特定环境的测试必须说明原因、启用条件和影响，并在验证报告中列为未执行。
- 测试名称使用英文 `snake_case` 表达场景、条件和预期结果；测试函数按第 3 节添加中文注释。
- 小型 fixture 靠近测试；大型 fixture 放入 `tests/fixtures/`，保持只读并注明来源和用途。
- 测试辅助代码只在重复且语义稳定时抽取，禁止建立不透明的通用测试框架。
- 测试文件同样采用 400/800 行软审查阈值；表格驱动数据和 fixture 可以例外。

### 5.3 开发验证与发布验收分层

- 每轮开发必须运行非空单元测试和本次变更相关的必要验证。必要验证按风险选择格式、lint、静态检查、目标集成/契约测试和最小只读冒烟；改动真实边界时不得以“只跑单元测试”为由跳过对应检查。
- 日常开发默认不重复运行发布级整体验收：production/release 构建、最终产物存在性、最终产物启动冒烟、跨平台候选、归档校验和人工最终复核。修改发布链路时运行相应的单元、静态和隔离契约检查，但修改本身不授权真实发布构建、E2E、打包或外部发布动作。
- Computer Use E2E、真实设备、真实宿主交互及同类重型、交互式或真实环境验收不得由日常开发、普通交付复核或发布链路修改自动触发。只有用户发起最终产物构建或发布准备时，才在首次发布构建前列出具体项目并询问本次是否启用；选择不得跨任务继承。产品规格或发布渠道明确要求的项目必须标为必需，不得进入可跳过分支。
- 构建/发布任务必须基于当前源码执行不可跳过的基础门禁：代码编译、非空单元测试、相关集成/契约验证、最终产物构建与存在性检查，以及真实最终产物的有限时只读启动冒烟。任一失败都阻断打包、上传、产物收集、签名和发布，人工选择不能豁免。
- 已启用或必需的手动验收只能在所需最终产物构建成功后执行，并且必须早于任何打包、上传、产物收集、签名或发布动作。失败、超时、取消或选择后未执行均为门禁失败；同一任务内不得通过关闭选择绕过。未启用且没有产品/渠道硬要求时，记录 `Not run`、原因和风险后可以继续。
- 开发验证只能证明当前变更达到实施门槛，不得记为 `Verified`、发布就绪或人工完成。未运行的发布级检查必须明确记录为 `Not run`、`Not applicable` 或 `Unverified`，并给出准确理由。
- 如发布前反复暴露同一类集成失败，应根据证据把对应检查前移到今后受影响的开发轮次；不得以恢复所有轮次无差别整体验收代替风险分层。

## 6. 规则例外

- 硬规则例外必须记录到当日 `docs/adr/YYYYMMDD_ADR.md`，包含被偏离的规则、理由、风险、适用范围、替代验证和恢复条件。
- 默认规则允许在计划或复核记录中说明局部理由，不要求正式决策记录。
- 例外必须尽可能小，不得从单个文件或模块自动扩张为整个项目。
- 临时例外必须有删除条件；没有明确恢复路径的例外按长期架构决定处理。
- 人工批准只授权采用例外，不会把失败或未执行的验证改判为通过。

## 7. 机械检查边界

- 可确定检查的规则应自动化，包括格式、lint、编译、非空测试、文档链接、必需文件、manifest 继承、开发门禁与发布门禁分层。
- `TODO`、`FIXME`、`HACK` 格式以及文档和源文件软行数阈值可以由脚本报告；软阈值只产生审查提示，不直接判定失败。
- 公共 API 文档缺失可以由语言工具链判定失败。
- 中文注释是否有业务意义、模块职责是否合理、函数思路是否充分，必须由人工或 Agent 语义审查，不使用字符数、注释比例或关键词数量伪装成质量检查。
- 自动检查失败必须返回非零状态并给出具体位置，不得只打印警告后宣称通过。
- 新规则只有在能够稳定判断、重复违规且人工容易遗漏时才升级为自动门禁。
- Harness validator 只检查模板和 bundled assets；真实下游代码仍由其工具链和交付流程验证。
