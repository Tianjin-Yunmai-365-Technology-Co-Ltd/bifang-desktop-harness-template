# 个人小工具 Harness Engineering

> 从真实意图、明确边界到可靠交付，为个人小工具建立可复用、可验证、可持续维护的工程环境。

## 1. 文档目的

这份文档用于指导个人小工具从立项、MVP 实现、真实验收、发布，到后续升级维护的全过程。

它不是某个项目的功能规格，也不是一份要求所有项目采用相同技术栈的模板。它定义的是一套稳定的判断方法：如何把真实需求转化为边界清晰的软件，如何让人和 AI 编码代理准确理解并执行这些边界，以及如何证明软件已经完成并能够继续维护。

本方法特别适合以下项目：

- 为自己或少量明确用户解决一个具体问题。
- 以桌面工具、命令行工具、脚本或终端工具形式交付。
- 由人确定意图和边界，Codex 等编码代理参与设计、实现、测试和维护。
- 希望快速交付，但不接受核心流程不可靠、版本混乱或项目无法接手。

Harness 本身也必须遵守 MVP 原则。项目很小时，Harness 应当简单；只有被实际问题反复证明有价值的规则、文档和自动化，才逐步沉淀为长期基础设施。

## 2. 什么是个人小工具 Harness Engineering

Harness Engineering 不是把提示词写得更长，而是设计模型周围的完整工程环境，使执行者能够：

- 看见正确的项目上下文。
- 理解真实目标和明确边界。
- 使用合适的工具和权限。
- 按可预期的流程推进工作。
- 从构建、测试和真实运行中获得反馈。
- 判断任务是否真正完成。
- 将决定和结果留给未来的维护者与下一次会话。

在个人小工具中，Harness 由七层组成：

```text
Intent → Boundaries → Environment → Execution → Verification → Memory → Lifecycle
```

对应七个基本问题：

1. 为什么做？
2. 到哪里停止？
3. 如何让执行者正确理解项目？
4. 完成目标的最短可靠路径是什么？
5. 如何证明它真的可用？
6. 下一次如何无损接手？
7. 软件如何升级、维护并与用户保持联系？

## 3. 核心信念

### 3.1 一个工具只解决一个明确问题

立项必须从真实问题出发，而不是从想使用某项技术、框架或 AI 能力出发。

工具的目标应该能用一句话表达，并同时包含：

- 谁在什么场景下使用。
- 提供什么输入。
- 获得什么结果。

如果一句话需要用多个“并且”才能说完，应优先拆分问题，而不是立即扩大项目。

### 3.2 先完成最短闭环

MVP 的价值是证明核心任务能从输入走到输出，而不是提前拥有完整产品形态。

最短闭环至少包含：

```text
真实输入 → 核心处理 → 可用输出 → 明确结果反馈
```

### 3.3 复用成熟能力，不重复制造非核心系统

如果操作系统、成熟软件、可靠库或标准工具已经能完成某个非核心环节，应优先通过清晰边界调用它，而不是重新实现。

复用不等于盲目增加依赖。每项外部依赖都必须回答：

- 它替代了哪部分复杂度？
- 它的安装、版本和失败方式是否可接受？
- 项目是否能够清楚检测并说明依赖缺失？

### 3.4 不为假想未来建设抽象

设置系统、插件架构、通用任务框架、复杂状态管理和跨平台抽象，不能仅凭“以后可能需要”进入当前版本。

抽象应来自已经出现的重复，而不是对未来重复的猜测。

### 3.5 极简不等于不可靠

以下通常属于 MVP 的核心可靠性：

- 不静默破坏已有用户数据。
- 不把失败报告为成功。
- 长时间操作不导致程序假死。
- 失败后能够安全重试或清楚停止。
- 输出结果可以验证。
- 发布物能够对应到明确源码版本。

以下通常属于功能扩张：

- 批量、历史记录和高级筛选。
- 主题、账户、云同步和多设备。
- 插件系统和通用配置中心。
- 自动更新、遥测和在线后台。
- 仅为潜在需求设计的多层抽象。

### 3.6 仓库是项目事实来源

关键意图、决定、约束、验证结果和技术债必须保存在版本化仓库中。只存在于聊天记录、人的记忆或临时终端输出中的信息，不能被视为可靠项目记忆。

### 3.7 用户认知是交付的一部分

用户应该能够清楚知道：

- 软件解决什么问题。
- 当前使用哪个版本。
- 本次升级发生了什么。
- 软件是否仍在维护。
- 遇到问题可以在哪里反馈。

## 4. 七层 Harness 模型

### 4.1 Intent｜意图

意图层定义软件存在的理由。

每个项目创建时必须明确：

- 唯一核心用户或用户群。
- 真实使用场景。
- 输入与输出。
- 当前痛点及其影响。
- 为什么现有方式不足。
- 一句话目标。

目标描述结果，不描述实现。例如“把单个 EPUB 转换成 Kindle 可用的 AZW3”，优于“使用 React 和 Rust 开发一个转换器”。

### 4.2 Boundaries｜边界

边界层定义本次做什么、不做什么，以及软件成立所依赖的前提。

每个 MVP 必须同时写出：

- In Scope：完成闭环所必需的能力。
- Out of Scope：本版本明确排除的能力。
- Assumptions：用户环境和输入必须满足的条件。
- Constraints：平台、路径、权限、依赖和交付限制。
- Success Criteria：可以客观验收的完成条件。

非目标不是永久禁止。它只表示当前版本不承担这部分复杂度。未来只有在真实需求出现并重新评估后，才能进入新的版本规格。

### 4.3 Environment｜环境

环境层让人和编码代理能够正确观察、理解和操作项目。

一个合格的小工具环境通常包括：

- 简短项目入口和运行方式。
- 当前产品规格及非目标。
- 清晰的源码地图和模块边界。
- 确定的构建、测试和发布命令。
- 必要的工具、依赖和权限说明。
- 可重复或至少可说明的开发环境。
- 与项目规模匹配的代理指引。

应采用渐进披露：先提供一张地图，再让执行者按任务读取更深文档。不要用一个庞大的说明文件塞入所有历史知识。

当项目只有少量文件时，不必为了形式创建复杂目录。随着项目变大，可以逐步增加短小的 `AGENTS.md`、架构地图、产品原则、活跃计划和技术债记录。

### 4.4 Execution｜执行

执行层定义如何以最短可靠路径完成工作。

默认原则：

- 优先简单、成熟、可直接理解的技术。
- 保持数据流短，模块职责单一，接口数量少。
- 在系统边界处校验输入和结果。
- 将平台相关行为集中到明确模块。
- 不把普通的单任务工具设计成通用平台。
- 不在没有真实消费者时增加扩展点。
- 对核心流程使用直接、可观察的实现。

执行期间若发现规格不足，应先更新意图或边界，再继续实现。不能通过临时代码决定产品行为，然后让文档被动追赶。

批准范围必须先拆成 Todo 批次和验证里程碑。Todo 记录预期行为、影响边界、验证方式和状态；任一 Todo 未完成时持续编码与非空单元测试，不得提前进入里程碑或执行冒烟/E2E。

### 4.5 Verification｜验证

验证层负责提供完成证据。构建成功不等于软件可用，测试通过也不等于用户目标已经达成。

验证分为四级，并受 Todo/里程碑状态机约束：

1. **静态验证**：类型检查、格式检查、lint、配置校验。
2. **自动测试**：覆盖核心状态流、边界计算和高风险失败点。
3. **构建验证**：生成真实交付格式，并检查版本、元数据和文件位置。
4. **里程碑真实验收**：全部 Todo 完成后，在目标环境中使用完整真实产物和真实输入完成批准场景。

Mock、stub、占位页面、中性 scaffold、开发预览和源码片段可以服务于开发，但不能作为里程碑验收对象。验收发现缺失逻辑或行为偏差时，应保存证据、重开 Todo、返回编码并增加回归测试，而不是用“部分通过”结束交付。

冒烟和 E2E 只属于验证里程碑。是否执行由项目持久策略、产品/渠道硬要求和场景适用性共同决定；产品定义、计划、Todo 编码、常规构建、制品收集和发布元数据流程不得自行触发。

测试数量不是目标。优先覆盖：

- 核心成功路径。
- 会造成数据损失的失败路径。
- 用户最容易误判结果的状态。
- 外部依赖缺失或失败。
- 版本升级可能破坏的既有行为。

任何完成声明都应说明实际执行了哪些验证，以及哪些验证因缺少环境或输入尚未执行。

### 4.6 Memory｜记忆

记忆层保证项目能够跨人员、机器和会话延续。

需要进入仓库的项目记忆包括：

- 当前规格和非目标。
- 重要技术决定及理由。
- 已知限制和技术债。
- 活跃计划及当前进度。
- 验证方法和最近结果。
- 版本历史和发布说明。
- 发布物与源码 commit 的对应关系。

文档必须有明确角色：

- 规格说明应该做什么。
- 源码说明实际做了什么。
- 测试说明哪些行为被机械验证。
- 变更记录说明各版本改变了什么。
- 计划说明尚未完成什么。

如果文档与源码冲突，应调查事实并修复其中一个，不能默认忽略差异。

### 4.7 Lifecycle｜版本、维护与用户关系

生命周期层从软件创建第一天开始，而不是等到“以后正式发布”再补充。

它负责：

- 语义化版本管理。
- 功能升级和缺陷修复策略。
- 发布说明和构建产物管理。
- 维护状态说明。
- 用户反馈和项目联系入口。
- 已发布版本的长期可追溯性。

## 5. MVP 范围闸门

任何拟加入当前版本的需求，都依次回答以下问题：

1. 没有它，核心用户能否完成唯一目标？
2. 它是在提高核心流程的正确性和可靠性，还是增加新的使用方式？
3. 需求来自真实使用，还是来自对未来的想象？
4. 能否通过已有系统或更简单的方式解决？
5. 它引入多少新的状态、依赖、权限和失败模式？
6. 它是否改变当前版本的成功标准？
7. 如果延后到下一个版本，用户会损失什么？

判断原则：

- 缺少它会导致核心目标无法完成：进入 MVP。
- 缺少它会导致数据损坏、结果失真或无法合理使用：作为可靠性工作进入 MVP。
- 它只是提供更多选择、更高级体验或潜在扩展：进入未来版本候选。
- 无真实证据且增加明显复杂度：拒绝。

## 6. 面向 Codex 的项目 Harness

### 6.1 人负责方向，代理负责执行

人的主要责任是：

- 选择值得解决的问题。
- 给出真实约束和取舍。
- 确认产品边界。
- 对用户体验和风险做最终判断。
- 验收结果是否解决真实问题。

编码代理的主要责任是：

- 阅读仓库事实。
- 提出可验证的实现方案。
- 修改源码和文档。
- 执行测试、构建和检查。
- 报告证据、风险和未完成事项。
- 将新知识沉淀回仓库。

### 6.2 给地图，不给百科全书

代理入口文档应短小，主要回答：

- 项目目标是什么？
- 关键文件在哪里？
- 哪些规则必须遵守？
- 应执行哪些验证？
- 深入资料在哪里？

详细内容应分散在规格、架构、计划、测试和发布文档中，并通过入口文档建立链接。

### 6.3 约束必须可检查

重要规则不能只写成希望。能机械检查的约束，应逐步转化为：

- 类型系统。
- 测试。
- 格式化或 lint 规则。
- 构建脚本。
- CI 检查。
- 发布清单。

只有当规则重复出现并且人工检查容易遗漏时，才值得自动化。

### 6.4 每次任务留下可接手状态

一次工作结束时，应明确记录：

- 修改了什么。
- 为什么这样修改。
- 执行了哪些验证。
- 哪些验证没有执行。
- 是否存在工作区未提交修改。
- 下一步是什么。
- 是否改变了规格、版本或技术债。

## 7. 标准三段式版本管理

个人小工具同样需要让用户能判断当前版本是否兼容、是否值得升级，因此版本管理不能是发布前临时补的动作，而应该从第一次可运行 MVP 起就存在。

版本管理的可执行规则（Harness 上海时区时间版本、下游 Semantic Versioning 2.0.0、已发布版本不可覆盖和发布门禁等）由 `docs/RELEASE.md` 统一维护；Harness 模板当前版本、时间版本起始值、旧版本标识与发布状态只由根目录 `Version.md` 记录。本节只保留为什么严肃对待版本号这一背景动机，不再重复具体规则，避免出现多份可能漂移的版本规范。

## 8. 发布物命名与版本认知

发布物命名同样只保留一份权威来源：Rust 下游产品的归档命名模式（`<product>-v<version>-<platform>-<arch>.<ext>`，附带 `.sha256` 与 manifest）已在 `docs/RUST_CLI_TEMPLATE.md` 给出，模板自身源码归档命名见 `docs/RELEASE.md`。

本节保留的背景动机是：文件名、Git tag 和发布标题里的版本必须让人一眼确认彼此对应。Harness 使用 12 位时间版本，下游默认使用 `MAJOR.MINOR.PATCH`，`v` 只是面向人识别的前缀；具体示例和字段级规则不再在此重复。

## 9. CHANGELOG 与升级说明

CHANGELOG 是用户和维护者感知“这个版本到底变了什么”的正文来源，缺失或敷衍会让升级和排障都失去依据。

可执行规则——按日文件命名、分类、何时必须更新、不兼容变化如何标注——已收敛到 `docs/changelog/README.md`，`AGENTS.md` 的事实来源表也指向该文件作为用户和维护者可见变更的唯一正文来源。本节不再重复具体格式，仅保留“为什么每次可感知变化都要留痕”这一原则。

## 10. 维护状态与用户建联

维护状态和反馈入口属于用户认知的一部分（见 3.7）：用户应当知道软件是否还有人维护、遇到问题去哪里反馈。

这条原则目前只是背景建议，不像本文档其他章节那样接入了具体门禁或 Skill，因此保持简短：README 至少标注一种维护状态（Active / Maintenance / Paused / Archived），并至少提供一种持久反馈入口；停止维护时保留历史源码并说明最后可用版本和已知重要问题。极简工具不应为了建联而增加账户、遥测或强制联网。

## 11. 最小项目资产

一个准备长期维护的小工具，建议至少包含：

```text
README.md                  用户用途、运行前提、使用方式、维护状态、反馈入口
docs/adr/                  按日保存已确认需求与重要决定
docs/changelog/            按日保存用户和维护者可见变化
docs/                      规格、重要决定和必要参考
src/                       源码
tests/                     核心闭环和风险测试
版本 manifest              唯一版本事实来源或受控同步来源
构建配置                   可生成真实发布物
```

按需增加而非默认增加：

- `AGENTS.md`：本 Harness 产出的每个项目都强制、永久包含该文件——其 Skills 地图与约束地图是 `AGENTS.md` 自身声明的永久结构，初始化与后续裁剪都不会移除它，这不是等待某个触发条件才增加的可选项；只有完全不经由本 Harness 生成、且从未有编码代理参与的项目，才需要自行判断是否引入等价文档。
- `ARCHITECTURE.md`：当模块关系已无法通过源码目录直接理解时增加。
- 执行计划：复杂、跨多步或需要跨会话推进时增加。
- CI：当人工验证开始重复、发布给其他用户或多人协作时增加。
- 自动发布：当手工发布频繁出错且发布频率足以抵消维护成本时增加。

## 12. 新项目启动模板

新项目启动时把“一句话目标、真实问题、输入输出、MVP 范围、约束、数据流、错误与可靠性、成功标准、验证、版本发布、用户建联、已知风险”逐项写清楚，这件事本身仍然成立；但对本 Harness 产出的下游项目，这份规格的采集、确认和落盘已经是 `$define-product` Skill 的可执行工作流——它会创建并综合 `docs/product_spec/` 的当日快照，而不是要求人工复制一份 Markdown 模板。本节不再给出模板正文，避免与 Skill 实际产出的规格结构出现两份可能不一致的版本；需要了解规格应包含哪些字段时，直接阅读 `$define-product`。

## 13. 阶段检查清单

立项、设计、实现、验证、发布、迭代维护六个阶段各自需要检查清单，这个判断仍然成立；但可执行版本已经分散到对应 Skill 中——立项与设计对应 `$define-product`，实现对应 `$plan-change`/`$implement-change`，验证对应 `$verify-delivery`，发布对应 `$prepare-release`（版本与发布规则见 `docs/RELEASE.md`），迭代维护同样回到 `$plan-change` 重新过一遍范围闸门（见第 5 章）。本节不再重复逐条清单，避免清单在这里和 Skill 里各更新一半。

## 14. Harness 的积累与演进

不是每次项目经验都应该变成永久规则。只有满足以下条件之一时，才考虑升级为通用 Harness：

- 同类问题在多个项目中重复出现。
- 问题造成过真实失败、返工或用户损失。
- 人工检查容易遗漏，且规则可以清楚验证。
- 新规则能降低未来项目的认知或交付成本。

沉淀顺序应由轻到重：

```text
经验记录 → 清单条目 → 项目规则 → 自动检查 → 通用工具
```

避免以下反模式：

- 因一次偶然问题增加永久复杂流程。
- 把个人审美包装成必须遵守的工程规则。
- 为了体现“工程化”创建无人维护的文档和脚本。
- 让 Harness 文档比实际项目更难理解。
- 规则已经失效但仍继续注入代理上下文。
- 自动化成本超过它预防的问题成本。

Harness 应定期清理。过时规则和错误上下文会比缺少规则更危险。

## 15. Agent-first 小工具设计

当小工具的主要使用者是 Codex、OpenClaw、Hermes 等 AI Agent，而 GUI 主要用于人类查看和管理时，产品边界、接口优先级和验收方式应当围绕机器调用设计。

Agent-first 不等于取消 GUI，也不等于把现有 GUI 操作机械地包装成自动点击。它要求先建立稳定、结构化、可验证的 shared core，再按真实消费者选择 CLI、TUI、MCP 或 GUI；没有选择时 Harness 默认 CLI。

### 15.1 先确定主要消费者

立项时除核心用户外，还必须明确主要消费者：

- 人类直接操作：GUI、TUI 或交互式 CLI 可以作为主要界面。
- 脚本和自动化：稳定 CLI 是主要契约。
- AI Agent：CLI 适合最广泛的进程调用，MCP 适合工具发现和结构化宿主集成；按目标 Agent 选择，不强制两者同时存在。
- 远程系统或多用户服务：只有这类真实需求出现后，才评估 HTTP API 或常驻服务。

主要消费者决定实现和验收顺序。若 Agent 是第一用户，不应先完成全部 GUI，再尝试从界面行为反推机器接口。

### 15.2 推荐分层

适合 Agent-first 小工具的最小结构是 Shared Core 加至少一个所选 adapter：

```text
                  ┌─ GUI：人类管理
统一数据存储 ← Shared Core ├─ CLI：脚本与通用兼容
                  ├─ MCP over stdio：可选 Agent 扩展
                  └─ TUI：终端中的人类界面
```

各层职责如下：

- **Shared Core**：业务规则、校验、应用服务、数据访问和平台能力。
- **CLI**：把核心能力暴露为非交互、可组合、可测试的命令。
- **MCP**：向 Agent 提供可发现的工具、参数 Schema、说明和结构化结果。
- **GUI**：提供可视化管理、浏览、批量选择、设置和关于信息。
- **TUI**：为偏好终端的人提供交互体验，不作为 Agent 的主要集成协议。

每个 adapter 必须直接调用 Shared Core；不要让任何接口通过启动或解析另一个接口间接访问业务。

### 15.3 接口选择

| 接口 | 主要消费者 | 默认定位 | 何时采用 |
|---|---|---|---|
| CLI | 脚本、CI、Agent | 空选择时默认 | 需要本地自动化、调试或最广兼容性时 |
| stdio MCP | 支持 MCP 的 Agent | 可选扩展 | Agent 需要工具发现、结构化参数和审批语义，且已通过范围闸门时 |
| GUI | 人类 | 管理界面 | 需要浏览、编辑、批量管理和可视反馈时 |
| TUI | 终端用户 | 可选接口 | 有真实键盘终端交互需求时采用 |

### 15.4 CLI 契约

项目选择 CLI 时应满足以下要求：

- 命令按稳定资源与动作组织，例如 `tool app list`、`tool app launch --id <id>`。
- 所有核心操作都支持非交互调用；不得在 Agent 模式中意外等待输入。
- 提供 `--json`，标准输出只包含机器结果，诊断和日志写入标准错误。
- 使用稳定 ID 标识资源；界面序号只是当前视图编号，不能作为长期身份。
- 时间使用明确时区的 ISO 8601 格式。
- 定义稳定退出码和结构化错误码，区分参数错误、资源不存在、权限不足、执行失败和数据冲突。
- 列表接口支持搜索、排序、分页，并允许调用方忽略未来新增字段。
- 删除、覆盖等破坏性命令要求显式确认参数，例如 `--yes`；非交互模式不能自行确认。
- 文档至少提供帮助文本、JSON 示例、退出码表和常见失败示例。

推荐的最小命令面：

```text
tool resource list|get|search|add|update|delete
tool resource run|launch
tool settings get|set
tool about --json
tool mcp
tool tui
```

具体命令由产品目标裁剪，不为了形式实现无消费者的操作。

### 15.5 MCP 契约

> 可执行的最小规则已同步到 `docs/RUST_CLI_TEMPLATE.md`；本节是背景与完整设计依据。

stdio MCP 由 Agent 宿主管理进程生命周期：需要时启动，连接结束后退出，不监听本地端口。

MCP 工具设计应遵守：

- 一个工具完成一个清晰动作，名称使用稳定的动词和名词。
- 输入参数具有严格 Schema、必填项、枚举、长度和格式约束。
- 返回结构化数据，不把面向人的整段说明作为唯一结果。
- 工具说明明确前置条件、副作用、是否幂等和可能失败方式。
- 读取、写入、执行、破坏性操作采用不同审批级别。
- 工具数量保持克制；优先覆盖核心闭环，不镜像全部内部函数。
- MCP 与其他已选 adapter 通过 Shared Core 共享相同业务规则、错误模型和权限边界；不得通过解析另一 adapter 的输出复用能力。

对“程序启动器”一类能够执行本机程序的工具，默认只允许启动已登记资源。新增可执行路径、修改路径、删除资源和携带危险参数应作为写入或高风险操作，由宿主请求用户审批。

### 15.6 单一数据事实来源

> 可执行的最小规则已同步到 `docs/RUST_CLI_TEMPLATE.md`；本节是背景与完整设计依据。

项目包含的 GUI、CLI、MCP 和 TUI 必须读取同一份数据，不能维护互相同步的独立配置。

小型本地工具可以使用一个统一配置或数据文件，但需要同时具备：

- 显式 `schemaVersion`。
- 向前迁移策略和不兼容版本提示。
- 写入前校验。
- 临时文件写入后原子替换。
- 跨进程互斥或等效并发控制。
- 损坏文件的清晰报错与可恢复备份。
- 对未知字段的兼容策略。

所有界面只能通过 Store 或 Repository 边界访问数据。若未来数据量、查询能力或并发需求超过单文件能力，应在这一边界后迁移到数据库，而不是新增第二份事实来源。

### 15.7 人类管理界面

GUI 即使是次要界面，也应让用户能够确认系统状态和纠正 Agent 产生的变更。

通用管理型 GUI 建议包含：

- 标题栏显示软件名、版本号和维护联系方式。
- 关于页面显示产品身份、当前版本、维护状态、核心能力、隐私或免责说明及反馈入口。
- 设置页面从少量真实设置开始，并保留清晰分组，不提前建设通用配置平台。
- 数据较多时使用 Grid：复选框、视图序号、名称、创建时间、修改时间、最后执行时间、备注和操作列。
- Grid 支持全选、简单搜索、列头排序、分页和明确的空状态。
- 批量操作只作用于当前明确选择，跨页全选必须清楚说明范围。
- 视图中的创建、修改和最后执行时间来自核心数据，不由 GUI 自己维护。

Windows 开机自启动等平台设置应封装在平台边界中，并明确启动后是显示主窗口、进入托盘还是静默运行。首版没有真实托盘需求时，不要因“以后可能需要”提前实现常驻托盘。

### 15.8 安全与可审计性

> 可执行的最小规则已同步到 `docs/RUST_CLI_TEMPLATE.md`；本节是背景与完整设计依据。

Agent 能调用不代表 Agent 应自动获得所有权限。至少检查：

- 是否仅允许操作已登记或明确授权的资源。
- 进程参数是否以参数数组传递，避免拼接成 Shell 命令。
- 写入和破坏性操作是否需要审批或显式确认。
- 返回结果是否包含资源 ID、动作、时间、成功状态和真实错误。
- 是否记录最后执行时间以及必要时的调用来源。
- 日志和 JSON 输出是否避免泄露令牌、密码和不必要的本机隐私路径。
- 并行调用是否可能竞争同一配置或启动重复进程。

若某项操作无法安全重试，应在 CLI 帮助和 MCP 工具说明中明确标注。

### 15.9 Agent-first 实现与验收顺序

新项目默认按以下顺序建立闭环：

1. 明确 Agent 要完成的唯一任务和允许的副作用。
2. 实现 Shared Core 和单一数据事实来源。
3. 询问 CLI/TUI/MCP/GUI 接口组合；显式选择时只建立所选接口，空选择时默认 CLI。
4. 为每个所选接口建立独立、可测试的 adapter，不让 adapter 相互依赖或解析输出。
5. 把批准实现拆成 Todo 批次；持续实现并以非空单元测试和相关检查把每项推进到 `done`。
6. 全批 Todo 完成后构建完整真实里程碑产物；按持久策略和硬要求决定启动冒烟/E2E，并执行真实场景验收。
7. 任一场景失败时重开 Todo 返回实现；全部重新完成后再验收完整里程碑。

所有 Agent-first 项目必须证明 Shared Core 与实际所选接口的闭环；以下条目按接口条件适用：

- 若包含 CLI：非交互调用能完成核心任务，JSON 输出可稳定解析，失败返回稳定非零退出码。
- 若包含 MCP：MCP 工具可被目标 Agent 发现并完成同一核心闭环。
- 若包含 TUI：键盘流程、尺寸变化、错误恢复和终端状态恢复可观察。
- 若包含 GUI：真实打包应用能启动，关键页面、权限拒绝、可访问性和关闭行为通过验收。
- 若包含多个界面：各 adapter 通过同一 Shared Core 观察一致的权威数据状态。
- 高风险操作会触发审批或被策略拒绝。
- 并发读写不会损坏统一配置。

### 15.10 新项目决策清单

- [ ] 已明确人类、脚本和 Agent 谁是主要消费者。
- [ ] 业务能力位于 Shared Core，而不是 GUI 事件处理器。
- [ ] 已明确选择 CLI/TUI/MCP/GUI 中的实际接口；空选择才默认 CLI。
- [ ] 每个 adapter 直接依赖 Shared Core，彼此不依赖、不启动也不解析输出。
- [ ] 若包含 CLI，CLI 支持非交互模式、结构化输出和稳定退出码。
- [ ] 已判断是否存在足以让 stdio MCP 进入当前范围的真实需求。
- [ ] 若包含 MCP，其工具面只覆盖真实核心闭环。
- [ ] 若包含 MCP，MCP 与其他接口通过 Shared Core 使用同一业务规则和错误模型。
- [ ] 所有界面共用一个数据事实来源。
- [ ] 配置具有 Schema 版本、迁移、原子写入和并发控制。
- [ ] 稳定 ID 与界面视图序号已经分离。
- [ ] 执行、写入和破坏性操作具有不同审批策略。
- [ ] GUI 显示版本、维护入口和可核对的真实状态。
- [ ] TUI 有真实用户需求，而不是为了“接口齐全”。

## 16. 案例：EPUB 转 AZW3

这是一个早期单文件工具（只把一个 EPUB 转成 AZW3、复用本机 Calibre、React 只调用两个原生能力）留下的历史案例，用来具体说明单一目标、复用成熟能力、明确边界、短数据流这几条原则（见第 3 章）在真实项目里长什么样，以及极简规格仍需覆盖长任务不阻塞界面、失败时是否保留旧文件、成功状态与后续动作一致等可靠性细节。

这个案例本身预设的是单进程 GUI 直接调用本机命令行工具，早于第 15 章确立的 Agent-first shared core + adapters 架构；本 Harness 当前的分层、接口选择和验收方式请以第 15 章为准，本节只作为背景例证保留，不再作为新项目应当效仿的结构范本。

## 17. 完成定义

一个个人小工具可以宣布当前版本完成，当且仅当：

1. 唯一核心用户能够完成目标。
2. 输出在真实环境中可验证。
3. 已知高风险失败不会被误报为成功。
4. 自动检查和真实验收均有记录。
5. 版本号、CHANGELOG、Git tag 和发布物一致。
6. 用户能够知道如何使用、当前维护状态以及在哪里反馈。
7. 仓库足以让下一位维护者或下一次 Codex 会话恢复上下文。
8. 当前版本没有混入规格明确排除的功能。

完成不是“再也不修改”，而是当前版本的目标和承诺已经闭环。后续功能升级必须重新经过意图、边界、验证和版本判断。
