# 构建 Tauri 发布候选

为 Tauri GUI 生成可追溯发布候选；不得把普通本地试包升级为发布任务，也不得把 macOS 交叉构建证据冒充 Windows 原生运行证据。

普通“构建/打包/首次安装试包”转到 `$desktop-build-tauri-local-install`。正式候选的 E2E 选择在本次请求已明确 `enabled`/`disabled` 时直接复用，否则在任何测试或编译前询问用户一次；`milestone_e2e` 只提供建议默认值。所有 GUI 候选的 `performanceSelection` 必须精确为 `enabled | disabled`：只在 `performanceSelection: enabled` 时记录 `performanceStatus: Unverified`，选择 `disabled` 时使用下一条 `Not run` 契约。当前候选目标包含 macOS 时 `macosSigningSelection` 必须精确为 `enabled | disabled`；不含 macOS 时为 `not-applicable`。这些候选构建只核对既有版本，构建不得提升版本。

## 工作流程

1. 读取批准的 GUI 产品/应用资料、存在时受保护的 `docs/GUI_SUPPORT_SURFACES.md`、`docs/AGENT_POLICY.md`、`docs/RELEASE.md`、Tauri 配置、根 Cargo/前端锁文件和分发渠道要求；只有 E2E、完整验收或发布被独立触发时才读取其相关验证记录。完整读取 [references/tauri-macos-windows.md](references/tauri-macos-windows.md)。从根 `Cargo.toml` 的 `[workspace.metadata.agent-first-harness]` 读取目标平台与接口。只有用户明确提出发布候选或准备并构建发布才进入本 Skill；普通本地试包转到 `$desktop-build-tauri-local-install`。进入候选流程后，在任何测试、编译或 `release/` 清理前运行 `python3 .agents/skills/desktop-prepare-release/scripts/release_context.py verify --project-root .`，只接受工作树 clean、当前具名分支等于远端动态默认分支、远端主分支与上下文 `expectedTag` 都指向当前 HEAD，且 `.harness/release-context.json` 工作树字节、HEAD blob 与 schema 一致的结果。锁定 `sourceCommit`、`releaseContextSha256`、`releaseReview` 与 `candidateSelections`；审查、性能和 macOS 签名选择及来源只能从上下文读取。所有 GUI 候选的 `performanceSelection: enabled | disabled` 由 prepare-release 锁定：产品/渠道硬要求强制为 `enabled`，否则在任何测试或编译前询问用户一次；目标含 macOS 时签名选择必须为 `enabled | disabled`，否则为 `not-applicable`。上下文/tag/远端未完成或选择适用性冲突时转入 `$desktop-prepare-release` 或报告 `Not ready`。随后单独解析本次 E2E 选择。同一 `sourceCommit` 重跑复用上下文，新发布重新生成。`system_notification = enabled` 且签名关闭时在任何测试或 bundle 前停止。构建 Skill 不自行执行发布语义审查，也不设置分支拓扑门禁。
2. 要求本次构建已由用户显式请求，项目根是独立 Git 顶层目录。以 `git status --porcelain=v1 --untracked-files=all` 明确复核 clean，把当前 40 位 HEAD 锁定为 `buildSourceCommit`，要求等于上一步 `sourceCommit`，并锁定 `releaseContextSha256`；dirty、无 HEAD、上下文/远端主分支/tag 不一致时停止。普通构建不得自行 add/commit 或配置身份。真实 GUI 包、前端锁文件和项目本地 Tauri CLI 必须存在。固定 os/updater/window-state/dialog 基线、权限和注册顺序继续按产品工程规则验证。先调用 `$desktop-manage-version check --phase build`，确认 Cargo 当前版本、版本状态和发布上下文版本一致；构建不得计算、提升版本或重置正式发布周期。随后只读运行 `release_notes.py check --file release-notes.json --expected-version <version>` 和 `verify_release_notes_resource.py config`，计算摘要；本 Skill 绝不得生成或改写它。按原有 GUI profile、DMG 背景/布局和 updater 配置要求验证，包括 `<project-id>_gui/src-tauri/dmg/background.png` 必须是非符号链接的 660×400 PNG；缺失或漂移时返回 `$desktop-prepare-release`。存在活动 Todo 时不得构建未完成范围。
   - 同一固定基线还必须包含 dialog：根 `tauri-plugin-dialog = "2.7.3"`、GUI member `workspace = true`、前端生产依赖 `@tauri-apps/plugin-dialog = "^2.7.3"`，中央 Builder 在 window-state 后、条件 notification/autostart/global-shortcut 前恰好注册一次。主窗口 capability 的 `dialog:*` 项必须精确为唯一 `dialog:default`，覆盖 message/open/save 全部官方对话框类型；禁止 wildcard、deprecated alias、deny 项和任何额外文件系统授权，dialog 不加入自有 `invoke_handler`。任一依赖、顺序或权限漂移都停止构建。
3. 从批准的产品事实解析 GUI profile 之外的 `updaterEnabled` 发布门。它只控制当前候选是否生成、签名和声明 updater archive，绝不能控制固定 updater 插件是否安装。若为 false，保留第 2 步基线与 `NotConfigured` 零出站行为，要求 `bundle.createUpdaterArtifacts` 未启用，不生成、签名或伪造更新制品，也不得留下会使运行时主动检查的 endpoint/pubkey 配置；若为 true，在任何测试前要求：Tauri 配置启用 `bundle.createUpdaterArtifacts: true`，官方 updater 插件具有非空公钥和受限 HTTPS endpoints，产品文档记录 channel/target/arch 与强更策略认证边界，源码/配置/前端不含服务端 secret 或发布私钥。构建运行时必须存在已批准的 `TAURI_SIGNING_PRIVATE_KEY` 安全来源及该密钥实际需要的密码来源；只探测存在性/可用性，不输出值、路径正文或派生私钥。任一条件缺失或 false 分支混入发布配置都阻断候选，不得通过删除固定插件、关闭签名验证、临时改写 `updaterEnabled` 或把外部浏览器下载冒充自更新来继续。
4. 在任何单元测试或构建命令前，按当前宿主选择本 Skill 随附的 release helper：macOS/Linux 调用 `scripts/prepare-release-directory.sh <project-root>`，Windows PowerShell 调用 `scripts/prepare-release-directory.ps1 -ProjectRoot <project-root>`，安全刷新项目根 `release/`。两者分别与 `$desktop-build-rust-release` 的 POSIX/PowerShell helper 保持逐字节一致，复用相同的 Git 根、clean HEAD、符号链接或重解析点、原子隔离和同根暂存门禁；其 `release.source_commit` 必须等于 `buildSourceCommit`。Windows 原生路线不得调用 `.sh` helper；不要求 GUI-only 项目保留 CLI 构建 Skill。
5. 初始化后的构建不做例行环境预检：不得因显式构建、目标包含 Windows x64、缺少/过期环境证据或工具链可能变化而调用 `$desktop-check-development-environment`。先使用当前环境运行下述真实 Rust、前端或 Tauri 命令；只有某条命令已经失败，且命令、退出状态和脱敏诊断明确指向受管 GUI 工具链或 xwin 工具缺失/不兼容时，才调用对应的常规或 `scripts/macos-tauri-xwin-gates.sh --install-missing --target x86_64-pc-windows-msvc` 门禁，并重试原命令一次。代码/测试、依赖解析、网络、配置、凭据、updater 签名、安装包签名或公证失败不得误判为环境错误；任一门禁或单次重试失败时停止，不临时拼装安装命令。
6. 打包前只先运行项目全部非空单元测试。Rust 必须以 `cargo test --workspace --all-targets --all-features --locked -- --list` 或等价方式确认非空，再运行 `cargo test --workspace --all-targets --all-features --locked`；前端必须运行 `package.json` 与锁文件实际声明的完整单元测试套件，不得使用文件过滤、单测试名、相关子集或 watch 模式，并须确认发现至少一个测试。完整前端套件始终覆盖所有可见版本恰有一个小写 `v`；`about_page = enabled` 时还必须覆盖 Rust 资源解析/畸形失败、handler 注册、前端固定 IPC 命令与解码、loading/error/retry、关于页“更新日志”按钮、近 5 版/每类 10 条上限和父容器不代理检查或日志按钮，disabled 时覆盖路由、命令、加载器、入口与运行时组件缺席。固定 updater 基线始终覆盖无发布配置时 `NotConfigured`、零出站、失败不伪报“已是最新”；`updaterEnabled: false` 还覆盖无 updater archive/签名生成配置，`updaterEnabled: true` 才另外要求更新状态、认证最低支持版本 SemVer 强更、签名/target/channel 拒绝和任务回收回归。另行启用统计时才要求产品级同意与零出站回归，默认设置页不得因此恢复隐私/统计区块。不得自动追加格式、lint、类型、中文注释、`dist` 扫描或其他开发门禁；任一单元测试失败或测试数为零时停止。测试完成后、任一正式 Tauri 编译前再次要求工作树 clean 且 `HEAD == buildSourceCommit`；测试产生变化时停止。不得启动安装包、应用或 Windows 二进制。
7. 在任何 bundle、签名、公证或 stapling 前，再次要求工作树 clean、当前分支仍为动态默认分支且 `HEAD == buildSourceCommit`。只有 `performanceSelection: enabled` 或产品/渠道硬要求时，才以项目本地 CLI 和同一 release 配置运行原生 `pnpm tauri build --no-bundle --config src-tauri/tauri.release.conf.json`。从真实输出/Cargo 元数据定位唯一 release-profile Tauri 可执行文件，计算其 SHA-256，并在项目根同级候选暂存目录创建只描述该探针的输入 manifest：至少包含 `performanceSelection: enabled`、普通 basename `performanceProbe`、`performanceProbeKind: tauri-no-bundle-executable`、`performanceProbeBuildProfile: release`、`performanceProbeSha256`、`sourceCommit: <buildSourceCommit>`、`sourceTreeState: clean`、原生 `platform`/`architecture`、`buildMode: native` 和本次 `e2eSelection`。随后调用 `$desktop-test-gui-release-performance`；性能已启用时，`milestone_e2e` 或本次 E2E 为 `disabled` 都不得跳过。该 Skill 必须在每次冷启动前恢复同一 window-state 测试种子，并在所有退出路径恢复、复核用户原状态；helper 返回 0、证据为 `performanceStatus: passed` 且原窗口状态恢复已验证，才可直接进入打包。窗口状态恢复失败不可由性能 waiver 绕过。
   - 探针无法观察、证据不完整或任一指标失败时，保留 `failed` 证据并返回 `$desktop-implement-change` 做一次有界修复和回归；修复会通过 `$desktop-manage-git-lifecycle start` 自动建立新开发分支。本轮上下文、tag 和候选立即失效；重新提交后完整执行 `$desktop-prepare-release`，从新的远端默认分支/tag HEAD 重跑测试、探针和打包。
   - 只有修复尝试后新的原生探针仍失败或无法观察，才向用户展示失败指标和剩余风险并询问是否继续。没有当前请求中的明确确认就停止；确认后只能记录 `performanceStatus: waived`、非空原因/确认时间/确认摘要/已尝试修复/剩余风险，并引用原始 `failed` 证据，绝不得改写为 `passed`。
   - macOS→Windows xwin 交叉产物不能使用 macOS 探针代证；性能启用时记录 `Unverified`。只有真实 Windows 从同一 clean、已推送且被版本 tag 指向的默认分支 HEAD 生成原生探针，才可得到 Windows `passed`/`waived`。
   - 选择 `performanceSelection: disabled` 且无产品/渠道硬要求时，不运行 `--no-bundle`、不调用性能 Skill，也不创建 `performanceProbe`、`performanceEvidence`、`performanceThresholdProfile`、`performanceWaiver` 或 `performanceRuntimeBinding`。记录 `performanceStatus: Not run`、非空关闭原因和剩余性能风险后直接进入打包；不得把同一候选已经产生的 `failed` 证据改写成 `Not run`，这种情况只能修复重建或走显式 `waived`。
8. macOS 原生候选必须通过上一步的 `bundle.macOS.dmg.background: "./dmg/background.png"` 引用项目内背景，并把 Finder 拖拽安装布局写入真实 DMG，而不是只在 Tauri 配置中声明背景和坐标。性能已启用时，打包开始前锁定已经通过或明确 waived 的性能探针字节；将进入 bundle 的未签名运行时必须与该探针逐字节一致。若 Tauri 打包阶段重新编译、改变配置/依赖/资源接线或产生不同运行时摘要，立即废弃性能证据并回到第 7 步以新字节重测，绝不得只因源码提交相同就复用旧结果。性能已关闭时不建立或伪造这种绑定。第 1 步已经锁定 `macosSigningSelection: enabled | disabled` 与来源：已批准的持久签名/公证配置为 `configured`，当前请求主动要求为 `requested`，渠道硬要求为 `channel-required`，其余固定为 `disabled/not-requested`；本阶段不得随后补解析或改变。交互式 macOS 构建的真实命令只允许来自下面对应选择分支，并必须为 Finder AppleScript 设置有界超时；Tauri 官方已记录布局开关在部分无交互 CI runner 上可能挂起，因此 headless runner 不得盲目启用。无可用 Finder 会话时，只能在签名/公证前使用项目自有、已测试且不含固定产品身份的确定性布局步骤，或者使构建失败；不得接受 `CI=true` 生成但缺少 `.DS_Store` 的空白 Finder 窗口。从 Tauri 真实输出定位唯一构建 `.app/Contents/Resources/release-notes.json`，立即运行 `python3 .agents/skills/desktop-build-tauri-release/scripts/verify_release_notes_resource.py bytes --source release-notes.json --bundled <discovered-resource>`；不得猜测 bundle 名称或只检查源配置。本机恰好存在身份、工具、环境变量或 Keychain profile 只表示可用性，绝不能自行改变选择。
   - 多个启用来源同时存在时，`macosSigningSource` 按 `channel-required > requested > configured > not-requested` 取最高优先级，使同一输入得到唯一可复核结果。
   - `disabled/not-requested`：不得运行 `scripts/probe-macos-notarization.sh`，直接以同一已批准 Finder 布局策略运行 `CI=true TAURI_BUNDLER_DMG_IGNORE_CI=1 pnpm tauri build --bundles dmg --no-sign --config src-tauri/tauri.release.conf.json`，记录 `signingStatus: unsigned`、`notarizationStatus: not-run` 和未签名风险；若渠道要求签名公证，此分支在解析阶段即被覆盖为 enabled。
   - `enabled`：才运行 `scripts/probe-macos-notarization.sh`。只接受 `ready` 后才以同一已批准 Finder 布局策略运行 `CI=true TAURI_BUNDLER_DMG_IGNORE_CI=1 pnpm tauri build --bundles dmg --config src-tauri/tauri.release.conf.json`；`unavailable`、探测失败或条件不完整都阻断，不得切换为 unsigned。环境变量三元组模式不传 `--skip-stapling`，让 Tauri 完成 Developer ID 签名、公证、等待和 stapling；若探测返回 `notarytool-keychain-profile`，Tauri 先完成 Developer ID 签名与 DMG 打包，再立即使用已批准的 profile 调用 `notarytool submit --wait`，只接受 `Accepted`，然后对 app/DMG 执行适用 stapling 与验证。不得输出或记录秘密/profile 名。
9. 启用 macOS 签名后绝不得输出仅 Developer ID 签名但未公证/staple 的候选。签名、公证、stapling、Gatekeeper/ticket 验证任一步失败都使该候选失败；不得以 `--no-sign` 重试或静默降级。候选构建中禁止 `--skip-stapling`。关闭选择的 unsigned 路线不是失败降级，而是探测前已确定并写入清单的默认路线。
10. Windows 原生 x64 候选只能在 Windows x64 宿主执行。PowerShell 中设置 `$env:CI = "true"`，再使用 `pnpm tauri build --bundles nsis --target x86_64-pc-windows-msvc --config src-tauri/tauri.release.conf.json`；本分支禁止 `--runner cargo-xwin`，固定记录 `buildMode: native`。渠道允许 unsigned 且没有已批准签名配置时显式追加 `--no-sign` 并记录原因；已有批准的非交互 Authenticode 配置时才允许签名，开始后失败必须停止。输出从真实构建输出或 Cargo 元数据发现，应用资源更新日志须逐字节比较。构建成功不证明安装或运行；在最终候选 E2E/验收真实执行安装和运行之前，固定记录 `runtimeVerification: Unverified`。性能启用时必须在同一 clean 已发布 `buildSourceCommit` 上运行原生探针并得到 `passed` 或明确 `waived`；关闭时记录 `Not run`。
11. Windows x64 交叉候选只使用 `CI=true pnpm tauri build --bundles nsis --runner cargo-xwin --target x86_64-pc-windows-msvc --config src-tauri/tauri.release.conf.json`。首次尝试使用当前 PATH；只有该命令已经因受管 xwin 环境问题失败并由第 5 步门禁成功恢复时，才把门禁返回的完整 `gate.path.prepend` 原样前置到单次重试命令的 PATH，确保 LLVM、NSIS 与刚安装的 `cargo-xwin` 均可解析。拒绝 `msi` 或 `all`；WiX/MSI 只能在 Windows 原生宿主生成。输出必须来自 Tauri 报告或 Cargo 元数据解析的 `target/x86_64-pc-windows-msvc/release/bundle/nsis/`，不得猜测文件名。还必须从该次 Tauri 输出或 bundle 元数据定位未安装应用资源根的唯一 `release-notes.json`，使用 `verify_release_notes_resource.py bytes` 与根事实逐字节比较；这只证明交叉构建资源，不能提升 Windows `runtimeVerification` 或性能状态。
12. Windows 交叉安装包只有在项目已有批准的外部非交互签名命令、工具和凭据全部就绪时才尝试签名并验证；开始后失败必须停止。条件不足且渠道允许时记录 `unsigned`。无论编译是否成功，`runtimeVerification` 均为 `Unverified`。性能选择为 `enabled` 时 `performanceStatus` 为 `Unverified`，不能声称 Windows 性能通过；选择为 `disabled` 且无硬要求时记录 `performanceStatus: Not run`、原因和剩余风险。
13. `updaterEnabled: true` 时，从每次 Tauri 构建的真实输出或 bundle 元数据发现当前 platform/target 的官方 updater archive 与相邻 `.sig`，不得猜测文件名或用安装包 checksum 代替 updater 签名。要求 archive/签名均为非空普通文件，使用配置中的公钥执行实际签名验证，并确认版本、channel、target、arch 与安装包一致；缺失、重复、无法验证或签名不匹配都使该平台 updater 候选失败。不得把 `TAURI_SIGNING_PRIVATE_KEY`、密码、私钥路径或私钥派生内容写入 manifest、日志或制品。
14. 对 macOS 最终 DMG，在所有会改变字节的布局写入、签名、公证和 stapling 完成后先运行 `scripts/verify-dmg-layout.sh <final-dmg> <project-root>/release-notes.json`；它必须只读挂载最终字节并确认非空 `.DS_Store`、`.background/background.png`、唯一顶层 `.app`、指向 `/Applications` 的拖拽目标，以及唯一 `.app/Contents/Resources/release-notes.json` 与根事实逐字节一致。若挂载要求接受 SLA，必须取得独立人工授权，helper 不得自动接受。检查失败时本次构建失败。随后才对最终 DMG/NSIS 及已启用 updater 的 archive/`.sig` 计算 SHA-256，在项目根同级、同一文件系统的唯一暂存目录形成安装包、更新制品、签名、相邻校验和，以及仅在性能启用且原生测量时存在的性能证据；此时不得先写入或替换项目根 `release/`。
15. 写 manifest 前再次运行发布上下文 `verify`，要求 `sourceCommit`、`releaseContextSha256`、`releaseReview` 与 `candidateSelections` 逐字段等于第 1 步，并重新执行 GUI/macOS 适用性检查。manifest 记录 `sourceCommit: <buildSourceCommit>`、`releaseContextSha256`、完整上下文选择及其投影，以及原有平台、制品、更新日志、性能、签名、公证和 `milestoneAcceptance: pending` 字段。审查启用时逐字段复制上下文证据；关闭时只复制原因/风险且证据缺席。性能和 macOS 签名字段同样从上下文原样复制。
   - 上述公证证据字段对 macOS 受签名选择约束：`disabled/not-requested` 时 `notarizationEvidence` 与任何探测派生的签名证据必须缺席，通用 `signingEvidence` 只能结构化记录选择、来源、unsigned 结论与风险；manifest 还必须精确记录 `releaseNotesVersion`、`releaseNotesSha256`、`releaseNotesPath: release-notes.json` 与 `releaseNotesResourceVerification: byte-identical`；`enabled` 时才要求完整签名、公证、stapling 和验证证据。
   - 原生 macOS 且性能启用时记录 `performanceStatus: passed | waived`、`performanceThresholdProfile: gui-release-v2`、`performanceProbe`、`performanceProbeKind: tauri-no-bundle-executable`、`performanceProbeBuildProfile: release`、`performanceProbeSha256`、结构化 `performanceEvidence` 及 `performanceRuntimeBinding`。`performanceRuntimeBinding.stagedUnsignedRuntimeSha256` 必须等于探针摘要；未签名最终运行时使用 `binding: byte-identical` 并要求包内摘要相同，签名改变字节时使用 `binding: verified-signing-transition` 并同时记录签名前相同摘要、签名后包内运行时路径/摘要与签名验证。安装容器摘要绝不得写入 `performanceProbeSha256`。
   - 原生 Windows 且性能启用时使用相同的 `performanceStatus: passed | waived`、`performanceThresholdProfile: gui-release-v2`、探针/证据与 `performanceRuntimeBinding` 契约，并把探针、clean HEAD、Windows x64 平台及进入 NSIS 的未签名运行时绑定；签名改变运行时字节时同样只能使用 `binding: verified-signing-transition`。原生 Windows 选择关闭时使用下一条 `Not run` 契约，不得误写为 xwin 的 `Unverified`。
   - 性能选择为 `disabled` 且无硬要求时记录 `performanceStatus: Not run`、非空 `performanceReason` 和 `performanceRemainingRisk`；`performanceEvidence`、`performanceProbe`、`performanceProbeSha256`、`performanceThresholdProfile`、`performanceWaiver` 与 `performanceRuntimeBinding` 必须全部缺席。
   - xwin 且性能选择为 `enabled` 时记录 `performanceStatus: Unverified` 与非空原因，且不得伪造原生探针、性能证据或运行时绑定；xwin 且性能选择为 `disabled` 时使用上一条 `Not run` 契约。另固定记录 `updaterEnabled` 与实际 updater plugin/Tauri 版本；启用时再记录 channel、target、arch、公开公钥指纹、archive/`.sig` 的相对路径、大小、SHA-256 和 `signatureVerification: passed`，但不记录任何私钥事实。macOS 完整路径只在 ticket 验证成功时使用 `notarized-and-stapled`；Windows 使用 `not-applicable`。

   所有上述条件分支完成后才把 manifest 写入同一暂存目录。写完 manifest 后必须按每份 manifest 枚举并复算安装包、更新制品、签名、校验和及适用证据的精确集合，要求全部为普通文件、无多余/缺失项且与最终摘要一致；随后才以不跟随链接的目录级原子替换提交到 `release/`。替换前的任何失败都不得在目标目录留下部分候选。
16. 重新枚举 `release/`，要求文件集与所有 manifests 精确相等；只有 manifest 按启用分支声明的性能证据文件才必须包含在精确集合中，关闭分支不得残留旧探针或证据旁路文件。只在当前 `release/` manifest、其声明的相邻制品证据和最终回复中记录环境变化、命令、Rust/前端全量单元测试数量、安装包、updater archive/签名、当次性能选择/状态及适用探针/证据/runtime binding、大小、摘要、签名/公证证据、源码提交、本次 E2E 选择、交叉构建限制和未验证平台。不得创建或更新 Product Spec、ADR、Changelog、Product Status、Work Plan 或 Verification。性能 no-bundle 探针只在当次 `performanceSelection: enabled` 或产品/渠道硬要求时成为打包前门禁，并且独立于冒烟/E2E；除此之外编译、签名与打包期间不得混跑冒烟/E2E。若本次 E2E 为 `enabled` 或产品/渠道要求，最终字节形成后立即交给 `$desktop-verify-delivery`，否则只在 manifest 和最终回复记录 `E2E: Not run` 与剩余风险并结束构建。

   同一输出还必须记录当次 `reviewSelection`/`reviewStatus`、适用 `reviewEvidence` 或 `Not run` 原因/风险，以及 macOS `macosSigningSelection`/`macosSigningSource`；关闭的审查或签名分支不得残留对应探测与证据字段。

## 边界

- 当前合同覆盖 macOS 原生 DMG、Windows 原生 x64 NSIS 与 macOS→Windows x64 NSIS；真实前向证据仍只覆盖既有路线，Windows 原生安装/运行、Linux GUI、Windows MSI 和其他架构保持 `Unverified`，直到对应最终候选 E2E/验收实际通过。
- 不自动安装 Homebrew，不创建、索取、导出、显示或上传安装包签名、公证或 updater 私钥凭据，也不修改项目签名身份。
- macOS 安装包签名意图与机器可用性严格分离：没有已批准持久配置、本次主动要求或渠道硬要求时固定 unsigned，并且不运行身份/凭据/在线公证探测；一旦明确启用则完整签名、公证、staple，任一步失败都阻断而不降级。
- 不创建标签、Releases、商店提交、更新 feed；也不移动标签、上传更新制品。只读验证发布生命周期已经推送的版本 tag，构建授权不等于渠道发布授权。
- 不生成、补写、重排或截断 `release-notes.json`；构建只校验、打包并记录其摘要，任何内容变化都必须回到发布准备与新候选流程。
- 固定 updater 插件安装与 `updaterEnabled` 发布门是两件事：所有 GUI 保留 Rust-only 插件与 `NotConfigured` 零出站基线，只有 `updaterEnabled: true` 才生成、签名和声明更新 archive。安装包代码签名与 updater 制品签名是独立门禁；安装包公证另按渠道门禁执行。渠道允许安装包 `unsigned` 不代表 updater archive 可不签名；发布门启用后签名制品缺失或验证失败必须阻断。
- 构建请求、执行、成功、失败、重试和结果本身不触发任何项目记忆；候选 E2E 与完整验收只把结构化证据和状态原子写入忽略的 `release/` manifest 及其声明证据。只有真实渠道发布成功或独立回顾审计，才由后续受管 feature 生命周期写入 tracked 发布/Verification/项目状态事实，且不得反向批准活动或历史候选。
- 普通构建永不自动暂存或提交工作树；只有用户明确提出发布时，才由 `$desktop-prepare-release` 先完成受控本地提交，再把 clean HEAD 交给本 Skill。
- 普通 Windows 本地试包由 `$desktop-build-tauri-local-install` 独立处理；不得为了满足本 Skill 的 clean HEAD、更新日志或性能/E2E 门禁而询问是否把任务升级为发布。
- 本 Skill 不创建标签、Releases、商店提交或更新 feed；只验证 Git 发布生命周期已推送的主分支和版本 tag。
- GUI 性能选择独立于 E2E。选择启用或产品/渠道硬要求时，门禁发生在同一 clean 默认分支 HEAD 的原生 release-profile no-bundle 探针与 bundle 之间，没有 `passed` 或引用原始失败证据的用户明确 `waived` 时不得打包；选择关闭且无硬要求时跳过整个探针链，必须以 `Not run` 和剩余风险交付，不能伪造或复用旧证据。
- stapling 与最终只读 Finder 布局检查均通过后的字节才是候选。此后任何布局补写、签名、公证、stapling 或重打包都会产生新候选并返回 `$desktop-verify-delivery`。

## 完成输出

报告 clean `buildSourceCommit`/HEAD、当次 `reviewSelection`/`reviewStatus` 及适用证据或 `Not run` 风险、固定 updater 插件基线与独立的 `updaterEnabled` 发布门、当次 `performanceSelection`/`performanceStatus` 及适用性能证据；同时报告 bundle/target、环境安装与复探、真实命令、Rust/前端全量单元测试、安装候选/哈希/manifest、macOS `macosSigningSelection`/来源/签名公证状态，以及仅在 `updaterEnabled: true` 时存在的更新 archive/`.sig`/签名验证、`runtimeVerification`、`milestoneAcceptance: pending`、本次 E2E 选择/结果和剩余风险；不更新项目记忆。
